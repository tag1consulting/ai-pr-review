# v2.7.0

## Added

- **Canonical-review reuse (GitHub)**: rerunning the review no longer always posts a new review object. A fully quiet rerun updates the existing review's body in place; a still-open finding is updated (with a reply on severity escalation) rather than reposted; a `fixed` finding that recurs gets a reply and its thread reopened; a `dismiss`/`false-positive`/`wont-fix`'d finding is never reposted, even a fuzzy-matched nearby one of a compatible category and no higher severity. Only a genuinely new finding — or one severe enough (High/Critical) to require visibility regardless of diff anchoring — triggers a fresh review, and the prior blocking review is dismissed only after the fresh review is confirmed to have actually posted. Set `AI_CANONICAL_REUSE=false` to disable. See [Features → Quiet reruns (GitHub)](../features#quiet-reruns-github). GitHub-only; GitLab/Bitbucket parity tracked in issue #710.
- `GITHUB_BOT_USERNAME`: override the login GitHub-side review-selection and thread-ownership checks treat as "this bot's own", mirroring the existing `GITLAB_BOT_USERNAME`. Needed by any consumer whose reviews post under a non-default identity.

## Fixed

- A top-level PR comment carrying several `/ai-pr-review dismiss`/`false-positive`/`wont-fix`/`fixed`/`feedback` lines only ever acted on the first line; the rest were silently ignored. Every qualifying line in the comment is now acted on, with one combined reply (issue #733).
- The review body's inline-ownership marker could push a rendered GitHub review body past the provider's 65,536-byte limit; the truncation reserve now accounts for it.
- Verdict recording (`dismiss`/`false-positive`/`wont-fix`/`fixed`) now seeds its verdicts map from every prior bot review, not just the canonical review's own body, so an unrelated marker-less review becoming canonical could no longer erase every earlier verdict.
- Canonical-review reuse's thread-ownership check compared GitHub's GraphQL-reported author login (`"github-actions"`) against a REST-style constant (`"github-actions[bot]"`), rejecting every real thread and making the feature a no-op in production. `resolve_stale` had the same pre-existing bug. Fixed everywhere via normalization (issue #717), and `resolve_stale` no longer re-resolves a thread the same run just kept alive (issue #718).

## Security

- **Fork PR checkout reopened a code-execution path in three native analyzers.** The `pull_request_target` workflow checks out untrusted fork-PR content inside a container holding `ANTHROPIC_API_KEY` and a `GITHUB_TOKEN` with `pull-requests:write`/`checks:write`. `phpstan`, `checkov`, and `tflint` all auto-discovered and executed config/plugin content from that workspace — the same class of bug already fixed for `eslint`. All three now run against a freshly created, empty, trusted config passed via an explicit CLI flag that always wins over the tool's own auto-discovery, regardless of trust context. This is an unconditional behavior change: a project's own `phpstan.neon`/`phpstan.neon.dist` is no longer honored (`PHPSTAN_LEVEL` always applies now). The `sarif-prep` workflow job also now clears `sarif-results/` before running its analyzers, closing a related path where a fork-committed SARIF file could survive as a corroborating finding (issue #739).
- The superseded canonical review could be dismissed before confirming the replacement review actually posted; the dismissal now runs only after a confirmed, non-degraded post.
- Several other canonical-review-reuse correctness fixes: double-matched threads, a failed comment update counted as successful, a reopened thread still dismissible in the same run, a watermark that could advance past a skipped write, and a fingerprint-drift case that could silently stop honoring an old dismissal (#720).

## Changed

- `GitHubProvider.list_bot_reviews()` and `_list_prior_bot_reviews()` now share a single paginated walk over `GET /pulls/{n}/reviews`, removing the risk of the two independently hand-written walks drifting apart.
