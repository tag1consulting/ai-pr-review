# Trust construction-time checking, not read-time re-derivation, against self-contradictory verdicts markers

Issue #755 added two guards against a review body claiming a finding both active and dismissed: one at construction time (`github.py`, scoped to the current run's own output, before it posts) and one at read time (`_canonical.py`, re-checking every historical body on every fold). The read-time guard turned out to fire on the ordinary case too — a human dismissal command's PATCH always adds a "dismissed" verdict to a body whose id-map already lists the finding, by design, which is structurally identical to the corrupted-body shape #755 was defending against (issue #771). Its detection test cannot tell the two apart: both produce the same "fingerprint rendered in this body's own id-map, verdicts marker says dismissed" shape, so a guard built on that test can only ever be all-or-nothing, and choosing "nothing" was silently deleting real dismissals.

We removed the read-time guard and kept only the construction-time one. It guarantees no future review can ever be *posted* self-contradictory — but that is narrower than #755's original property, and we say so plainly rather than imply otherwise: it does **not** cover the suppression path. `classify()` short-circuits an exact or fuzzy `"dismissed"` match straight to `kind="suppressed"`, before the construction-time check ever runs, so a phantom `"dismissed"` entry of unknown origin (#755's own trigger was never confirmed) can still cause a live finding to vanish with no automated guard catching it — only a `_log.info` at the actual suppression site (`github.py`) as a forensic trail, plus the read-time site's own `_log.info` (downgraded from the removed guard's `_log.error`) logging the same shape earlier in the pipeline. This is a deliberately accepted residual risk: the removed guard's false-positive cost (silently eating real dismissals, #771 — the common case, not an edge case) outweighed a suspected corruption bug that was reported exactly once and never reproduced.

**Considered and rejected:** keeping both guards for defense-in-depth. The council review that preceded this decision raised exactly that concern, but the read-time guard's own test has no way to discriminate a correct dismissal from an incorrect one — a hypothetical bug that dismissed the *wrong* fingerprint would produce an identical shape to a correct dismissal, so keeping it protects nothing beyond what it already destroys. The narrower, adjacent risk that concern was really pointing at — a slash command acting on a garbage or unresolvable finding ID — is already independently guarded by `classify_finding`'s `UNKNOWN`-location short-circuit in `slash/dismiss.py`, which runs before any verdict is written.

**Considered and rejected:** re-adding a drop-based guard at the suppression decision point (`classify()` or the `github.py kind == "suppressed"` branch) instead of at read time. Moving the same id-map-co-occurrence heuristic elsewhere in the pipeline does not fix its core defect — it still cannot discriminate a corrupted phantom entry from a legitimate PATCH, since both produce an identical fingerprint match against `verdicts`. Any drop-based guard built on that heuristic reintroduces #771 regardless of where in the pipeline it runs. Observability (logging), not detection, is what the current design provides for this path.
