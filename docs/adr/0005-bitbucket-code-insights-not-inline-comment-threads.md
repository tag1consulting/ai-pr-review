# Bitbucket findings display via Code Insights annotations, not inline comment threads

Bitbucket Cloud's API can do real inline PR comments, threaded replies, and thread resolution -- the repo's own pre-Phase-3 docs (`docs/bitbucket-setup.md`, `ai_pr_review/vcs/bitbucket.py`'s module docstring) asserted the opposite, which was wrong. The first draft of the Bitbucket-parity plan (issues #839/#873/#874) took that discovery as license to rebuild GitHub/GitLab's comment-thread architecture on Bitbucket: real inline comments, a `PriorThread` parser, resolve-on-verdict, the full machinery. That direction was discarded after a structured review surfaced three facts, confirmed against Atlassian's own Code Insights documentation:

1. Annotation upsert is native and idempotent: `PUT` a report and `POST` its annotations, and re-running does not duplicate anything -- rendering a finding every run is free.
2. Annotations are not repliable. There is no thread to build or resolve, and therefore no place for "resolve" semantics or a keep-alive-set race to exist in the first place.
3. Cross-run dedup (#839) and a verdict mechanism (#874) do not actually require comment threads. They require (a) stable per-finding identity across runs, which the existing id-map/F-ID/fingerprint machinery already gives for free, and (b) a place for a human to type a verdict, which the existing single summary comment already gives.

We chose to keep display and state separate: Code Insights annotations became the inline display layer (native diff decoration, rebuilt from scratch every run via DELETE-then-PUT-then-POST), while the single summary comment remains the state/verdict layer exactly as it always was, carrying the id-map and (Phase 1) the hidden verdicts marker. `ai_pr_review.vcs._canonical.classify()` is reused as-is for the suppress/recur/new decision, called with `all_threads=[]` since there is nothing to fuzzy-match against.

This is architecturally smaller than the discarded thread-based design: no `PriorThread` parser for Bitbucket, no per-comment resolve-in-place logic, and the "Finding-0" `resolve_stale` keep-alive hazard -- which has already shipped as a real bug twice, once on GitHub (#718) and once on GitLab from day one -- does not exist here, because there is no thread state to race against. This eliminates that specific hazard class, not every race: two overlapping runs on the same PR can still interleave their DELETE-then-PUT-then-POST cycles against the same report, and a run killed between its own DELETE and PUT briefly leaves the PR with no report at all (the 403/404 fallback only covers an HTTP error, not a process dying mid-cycle). Neither is new to this design -- the same overlapping-run problem exists for GitHub/GitLab's own review posting, which is why `docs/features.md`'s "Concurrency note" recommends a Pipelines/Actions concurrency guard keyed on the PR number -- but Bitbucket's own docs did not carry that same recommendation before this ADR, and now do.

**Considered and rejected: real Bitbucket inline comment threads**, mirroring GitHub/GitLab exactly. Discarded per the three facts above: it would have required porting `PriorThread`/thread-resolution machinery for no corresponding gain, since the actual product requirements (dedup, verdicts) don't need thread state to satisfy, and it would have reintroduced the exact keep-alive hazard class this design avoids by construction.

**Considered and rejected: shipping `AI_BITBUCKET_CODE_INSIGHTS` default-off** for a staged rollout, the way GitHub/GitLab's inline-comment work defaulted off before flipping on. That pattern exists because a real comment thread visibly clutters a PR's Conversation tab the moment it's enabled -- Code Insights posts to a separate Reports tab and has a designed fallback to the pre-Phase-3 body-only behavior on any failure (a 403/404 falls back to rendering every finding in the summary comment, never silent data loss), so the clutter risk that justified a staged default-off rollout doesn't transfer. The residual risk of genuinely new code hitting a live Bitbucket API endpoint is addressed by a live e2e verification pass required before this phase merges, not by shipping the feature off by default for a release cycle.

**Considered and rejected: a second flag splitting annotation posting from the `classify()`-based suppression/dedup**, mirroring `AI_GITLAB_CROSS_RUN_DEDUP` being deliberately separate from `AI_CANONICAL_REUSE`. That precedent's own rationale is "coupling two independently-risky features would block rolling either back alone" -- and on GitHub/GitLab that's real, because their comment-thread posting can keep working perfectly well with dedup turned off. Bitbucket's situation is different in the one way that matters for this argument: the failure mode a second flag would exist to route around -- Code Insights being unavailable or broken on a given workspace -- is already handled automatically by the 403/404 fallback inside `post_code_insights` itself, with no flag flip required. An operator does not need `AI_BITBUCKET_CODE_INSIGHTS=false` to survive that case. The code already falls back to the pre-Phase-3 body rendering on its own. The scenario a second flag would actually protect against is a hypothetical operator flipping the flag off for some *other* reason and being surprised that previously-dismissed findings reappear -- a real but narrow surprise, not an operational necessity, and one documented plainly here and in `docs/bitbucket-setup.md` rather than engineered around with a second flag whose only job would be letting someone keep dedup while not exercising the one thing (annotation posting) dedup exists to declutter.
