# Fork PRs are reviewed in one deprivileged job, not a two-job split

Before this change, the engine paused every fork PR until a maintainer added a label for one exact head commit. The maintainer rejected that flow. A stranger's fork should get a review with no maintainer action, as long as spend is capped and prompt injection is contained. There must be no separate API key.

We decided that `auto` (the new default of `AI_FORK_POLICY`) runs a fork PR in the same job that holds the secrets. The engine restricts that run from inside. Every analyzer and git subprocess gets an allowlist-only environment, so no LLM key and no `GH_TOKEN` is in reach. Only analyzers with trusted or isolated configuration run. The prompts drop the PR body, commit messages, open-issue titles and branch name. The review event is capped at COMMENT, suggestions are off, and the output carries a fixed banner. Spend is bounded per run, per PR, per author and per day, and the engine fails closed when it cannot read its own state. Issue #1098 tracks the two-job split, which is a later option.

**Considered and rejected: label approval** (`AI_FORK_POLICY=label`, the old `approve` value). It needs a maintainer step for every fork PR and every new commit. That cost is the reason for this change. The policy stays available for repositories that want it, but it is no longer the default.

**Considered and rejected: the two-job split** (issue #1098). A `prepare` job without secrets would read the fork tree. A `review` job would get only the sanitized result. This is the stronger design, because a flaw in the engine process would not reach the secrets. It also needs a new workflow contract for every consumer, artifact passing between jobs, and a second runner start. We deferred it. The single job ships now with the limits listed below, and #1098 can replace it without a change to the policy names.

**Considered and rejected: a separate API key for fork PRs.** A key with its own limit would bound the spend at the provider. The maintainer does not want to create or rotate another key. A second key also does not help against a leak, because a leaked key still pays for the attacker.

**Considered and rejected: per-PR caps only.** A cap on each PR is easy to build. An attacker can open many PRs, or use many accounts, and the total spend has no bound. The author cap and the daily cap close that gap.

**Considered and rejected: a prompt-injection detector.** A classifier would add cost and false positives. It cannot give a guarantee, and an attacker can test against it. The design limits what an injected review can do (COMMENT only, no links or images, no suggestions, no secrets in reach) and does not try to stop the injection.

**Consequences:** The review runs in the same job as the secrets. The environment scrub covers subprocesses. A flaw in the engine process itself is not contained, and this is the main reason for issue #1098. The caps are best effort. A user with write access can edit or delete a ledger comment or a spend entry, and the cap then resets. Enough accounts can use up the 50 USD daily cap, which pauses fork reviews until the 24-hour window moves on. Trusted authors are not affected, because they do not count against the daily cap. The 70 percent reserved share keeps CONTRIBUTOR authors from being crowded out by first-time accounts. Forks get fewer static findings, because eslint, golangci-lint, semgrep repo rules, shellcheck, hadolint and kube-linter are skipped until each has a trusted configuration. The summary names the skipped analyzers. Prompt injection stays possible. It can make the review say nothing, or something misleading, about the fork's own PR.
