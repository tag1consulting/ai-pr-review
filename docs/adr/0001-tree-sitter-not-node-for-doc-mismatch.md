# Documentation-comment mismatch checking uses tree-sitter, not a Node/ESLint layer

We needed doc-comment/signature mismatch detection across `@param`-family languages (JS/TS, Java, Kotlin, C#, Ruby, C++, Scala) with no LLM cost. `eslint-plugin-jsdoc` is the best-in-class checker for this, but it requires a Node runtime, which this image does not have. We built a single tree-sitter-based engine instead (`tree-sitter-language-pack` is already a container dependency), covering all target languages uniformly with no new runtime.

Node was rejected on measured cost, not principle. No genuine single-binary Node distribution exists (even Node's Single Executable Applications feature embeds the full runtime). The only `COPY --from`-compatible option for this image's glibc final stage is `node:*-slim` at ~77MB compressed (~4x ruff, ~7x lychee), since the smaller alpine build is musl-linked and fails on a glibc host. npm cannot match this repo's existing pip/composer deterministic-pinning pattern (`npm ci` needs a committed `package-lock.json`, and `npm install --no-save` only pins top-level versions). And `@typescript-eslint/parser`'s peer range (`typescript <6.1.0`) is already incompatible with current TypeScript (7.0.2). Measured against this repo, doc-comment mismatch findings were 4 total across 82 files, none in JS/TS: no evidence of a coverage gap the added cost would close.

**Consequences:** JS/TS mismatch detection is homegrown (tag/name diffing over a tree-sitter parse) rather than the ecosystem's most mature tool. If false negatives show up in production for JS/TS specifically, adding a Node-based layer on top of the tree-sitter floor is a clean, isolated follow-up, not a rearchitecture.
