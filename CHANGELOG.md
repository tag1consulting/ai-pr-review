# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.0.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Changed

- **Fork pull requests are now reviewed automatically (`AI_FORK_POLICY=auto` is the new default).** Before, the engine paused every fork pull request until a maintainer approved the head commit. Now a fork pull request gets a review at once. The engine limits the run. Every analyzer and git subprocess gets a scrubbed environment. Only analyzers with a trusted or isolated configuration run on a fork. The prompts carry no PR body, commit message, open-issue title or branch name. The review event is COMMENT, suggestions are off, a fixed banner starts each comment, and the text has no external link or image. Spend is capped per run (2 USD), per pull request (4 runs and 6 USD), per author (2 open pull requests) and per day (50 USD). A pull request that reaches a cap pauses, and a maintainer resumes it with `/ai-pr-review rescan`. `OWNER` and `COLLABORATOR` authors are trusted and get the normal pipeline. To keep the old behavior, set `AI_FORK_POLICY=label` and keep the approval workflow. The `approve` value is now `label`. Set `block` to switch fork review off. See `docs/fork-prs.md` and `SECURITY.md` for the limits that remain, including that the review still runs in the job that holds the secrets (issue #1098).
- **Upgrade notes for the fork change.** `AI_FAIL_ON_FINDINGS=true` now also exits with code 2 when an agent returns output that the engine cannot read, because that run now posts COMMENT. A custom bot identity must set `GITHUB_BOT_USERNAME`, because the engine now ignores summary and skip comments from any other login. The checkout step must set `persist-credentials: false`, or a fork review pauses. The standard proxy and certificate variables reach analyzers, but a proxy value that holds credentials does not. The outbound secret scrub and the size limit on posted strings now apply to every run. The `@mention` and `owner/repo#N` neutralizing applies to fork runs only. The fork approval workflow (kept as an example in `examples/workflows`) and the `statuses: read` permission are needed only under the `label` policy. A repository that sets `AI_FORK_POLICY` to a non-default value must also set it for the `/ai-pr-review rescan` step.

## [2.24.1] - 2026-10-21

### Security

- **The PR checkout can no longer shadow the engine's Python modules.** The review starts the Python engine in the checked-out tree of the pull request. `python3 -m` puts the working directory first on `sys.path`, so a file in the pull request, for example `ai_pr_review/__main__.py` or `yaml.py`, could run instead of the installed module. That code would run with the review's API keys in its environment. The image, the container action, the root action and the `parse-command` step of `slash-commands.yml` now set `PYTHONSAFEPATH=1`, which keeps the working directory off `sys.path`. The fix reaches an image user only through the new image tag, so update `image-tag` to `2.24.1` or leave it at `latest`. A user of `container-action` from `main` is covered at once, because the action passes the variable to `docker run`. If you run `python3 -m ai_pr_review review` by hand from a checked-out tree, set `PYTHONSAFEPATH=1` first. The GitLab and Bitbucket example pipelines now do this (#1093).

## [2.24.0] - 2026-10-19

### Added

- **A provider "prompt too long" rejection now skips the review (#1056).** The pre-flight estimate can be too low. Before, the provider rejected the prompt with an HTTP 400, every agent failed, and the comment said "0 findings, 2 failed agents". Now the engine recognizes the rejection, stops, and posts a skip comment that names the agent, the model, and `AI_EXCLUDE_PATTERNS`. The comment also carries the analyzer and SARIF findings. The run does not advance the watermark. `AI_FAIL_ON_CONTEXT_WINDOW=true` makes this skip exit with code 2. With `AI_FAIL_ON_FINDINGS=true` this skip also exits with code 2, because no agent reviewed the PR. That is the same exit code as the failed run had before. Only the Anthropic message text is matched, and only for the Anthropic provider. The OpenAI, Google and Bedrock texts are not confirmed, so those providers keep the old behavior. The pr-summarizer, the issue-linker, and the judge pass also continue when the provider rejects their prompt, so the main agents reach this skip. If only some agents are rejected, the review continues and the failed-agent note says "prompt too long for the model".
- **Bitbucket: the `/ai-pr-review feedback [F<n>] <text>` command (#933).** The poll saves the text to the learning-loop store, as GitHub does. The text is required. An `F<n>` is optional. The command uses the same authorization as `false-positive` and `wont-fix` (the owners file first, then the permission lookup). It writes only when `AI_FEEDBACK_LOOP=true` and `AI_BITBUCKET_VERDICTS=true`. Two bare feedback lines in one comment are saved as two entries.
- **The `COST_ESTIMATE` log line ends with `input=` and `output_cap=` (#1055).** The two fields split the total into the cost of the estimated input tokens and the cost of the output cap. The existing fields keep their order. The configuration page has a worked example that turns a dollar ceiling into an input token budget. A new setting for an expected-value output estimate is not part of this release.

- **A new analyzer, `suppression-check`, flags a comment that turns off a security rule (#1077).** It reads the added lines of source files. It reports `noqa` with an `S` code, `nosec`, `nosemgrep`, `phpcs:ignore` or `phpcs:disable` on a security sniff, and `eslint-disable` on a security rule, at Medium. A finding names the directive and its rule codes and never quotes other text from the comment. The merge never clusters these findings. The number of analyzers is now 18. A workflow with an explicit `analyzers` allowlist must add `suppression-check` to get it.
- **A `crypto` finding category (#1076).** It covers weak hashes, weak or predictable randomness, and insecure token or key handling. The agent prompts name it, semgrep maps its md5, sha1 and `math/rand` rules to it, and Bitbucket shows it as a `VULNERABILITY` annotation. An older engine that reads a newer comment marker treats the unknown category as no category.
- **A finding can carry `impact` and `trigger` (#1078).** `impact` says who is harmed and how. `trigger` gives an example input or call that reaches the defect. Both are optional, one sentence each. GitHub and GitLab inline comments and the review body show them before the remediation. Bitbucket annotations do not carry them, because of the 450-byte limit, and the shortened body bullet for an annotated finding leaves them out too. They do not change the fingerprint, the clustering, the judge, or any approval decision. The prompts also ask for one kind of defect in each finding.
- **The code-reviewer checks that a value that one function writes and another reads agrees (#1079).** It compares the transport (cookie or header), the name, any prefix such as `Bearer `, and the format. A login route that sets a cookie while the admin route reads a header is the example.
- **A harness to measure a verifier that re-reads the code (#1082).** `tests/canary/verify_eval.py` replays the saved reviewer responses and compares a narrow and a wide window of the diff. It is a measurement tool and changes no review behavior. A billed run needs approval, and scoring against the hand-read verdicts of #837 needs those verdicts in the repository first, so #1082 stays open.

### Changed

- **Behavior change: a style or documentation finding no longer merges into a nearby security finding (#1074).** Before, the category `other` matched every category, so a phpcs "Missing doc comment" finding within 3 lines of a security finding joined it. The phpcs text won the headline on a tie, the security text was dropped, and the finding showed "corroborated by analyzer". Now a `docs` finding, and a finding that an analyzer marks as style only, cluster only with style findings of their own category. The analyzers decide per rule, because ruff, eslint, phpcs, shellcheck and hadolint use the category `lint` for style and for real defects. The style rules are the phpcs sniffs in the `Commenting`, `WhiteSpace`, `Formatting` and `NamingConventions` categories, the ruff formatting, naming, docstring, import and quote codes, the eslint formatting rules, and the shellcheck and hadolint findings at the `style` level. A rule that finds a defect, such as ruff F821, a ruff `S` security code, or eslint `no-eval`, is not style only and still merges with the agent finding for it. The headline is still chosen by severity alone. When an analyzer wins, the text of the dropped agent finding goes to the "Also reported by" lines. A finding counts as corroborated only when an analyzer and an agent describe the same kind of defect: equal real categories, or one real category and `other`. Two `other` findings do not. Fewer findings show as corroborated, and the badge reads the same flag. A finding that an analyzer and an agent both reported but that is not corroborated shows the label `analyzer and agent, not confirmed`, not "single agent". semgrep maps the PHP `exec-use`, `unserialize-use`, `system-use`, `backticks-use` and `eval-use` rules to `injection`. The headline text of some clusters changes, so their fingerprints change once on open PRs, and the line-based match recovers most threads.
- **Behavior change: phpcs sniffs in the `Commenting`, `WhiteSpace`, `Formatting` and `NamingConventions` categories are Low (#1075).** Before, every phpcs `ERROR` was High, so a missing docblock was High. The other sniffs keep `ERROR` to High and `WARNING` to Medium.
- **Repeated semgrep findings of one rule roll up in each file (#1081).** Two or more hits of the same rule in one file become one finding at the first line, with all the lines in its text. Before, the rollup needed more than 5 identical messages, and a semgrep message names its site, so it never matched. The text of a rolled-up finding is new, so its fingerprint changes once, and a dismissal still applies through the location match while the lowest line is the same. Only the first site gets an inline comment. The other sites appear as line numbers in its text. Findings that are corroborated or have more than one source stay out of the rollup.
- **A destructive shell command that an empty argument can aim at `/` is Critical (#1080).** The edge-case-hunter and the shell profile now rate `chmod`, `chown` and `rm` on `$DIR/*` with an unchecked positional argument as Critical when the script can run as root or as a deploy user. Before, the same finding was Medium.
- **Behavior change: the severity icons are different shapes (#1037).** Critical is ⛔, High is 🚨, Medium is 🔶, and Low is 💬. Before, three of the four icons differed only by color. 🚨 meant Critical before and means High now. A review comment that was posted before the upgrade keeps its old icon until the next review rewrites it, so an old 🚨 means Critical. No parser reads the icon.
- **The `also_reported` notes are capped only when they are shown (#1047).** A finding that two or more analyzers reported keeps every note, up to 100, and the review shows the first 5 with a "(+N more from other analyzers)" line. Before, the count in a merged finding was too low when a cluster had more than 5 notes.
- **The example workflows pass `approval-ceiling` (#1064).** `examples/workflows/pr-review.yml` and `comment-triggers.yml` read `vars.AI_REVIEW_APPROVAL_CEILING`, with `approve` as the fallback. An organization-level variable now covers every repository that copies the example.
- **The phpcs analyzer code is split (#1047).** The ruleset and pattern code moved to `_phpcs_ruleset.py` and `_phpcs_patterns.py`, and the retry rebuilds the plan from stored inputs. Behavior is unchanged. The security canary has a new symlink case and a test that runs the real phpcs with a hostile ruleset.

## [2.23.2] - 2026-10-19

### Security

- **Bitbucket verdict owners: `@nickname` lines no longer grant, and the owners file is read from the target branch only.** This is a behavior change. A nickname is not a unique identifier, so an `@nickname` line on a `*` line of `.bitbucket/CODEOWNERS` no longer authorizes a commenter. Only an `account_id` or a `{uuid}` grants. The review logs a warning that names each ignored `@nickname`. Replace each one with an `account_id` or a `{uuid}`. A person who is listed only by nickname gets the permission lookup, so they see the "not listed" reply until you change the file. The owners file is now always read from `origin/<BASE_REF>`. It no longer follows `AI_POLICY_SOURCE`, and the file in the pull request checkout is never read. A pipeline that set `AI_POLICY_SOURCE=workspace` and relied on an owners file in the pull request must merge that file into the target branch. This closes two ways in which a commenter could pass as an owner in v2.23.1. `policy.yml` still follows `AI_POLICY_SOURCE`.

## [2.23.1] - 2026-10-19

### Added

- **Bitbucket verdict commands are authorized from `.bitbucket/CODEOWNERS` (#1068).** Bitbucket allows the permission lookup that checks a commenter only for repository admins. A bot account with write access got HTTP 403 for every commenter, so no `/ai-pr-review` verdict command could be applied. The review now reads the owners first from the `*` lines of `.bitbucket/CODEOWNERS`. An owner can be an `@nickname` (ASCII), an Atlassian `account_id`, or a `{uuid}`. A listed commenter is authorized with no API call. Anyone else is checked through the old lookup. The file is read from the source that `AI_POLICY_SOURCE` selects: the target branch for `base-ref`, or the checkout for `workspace`. Under `workspace`, a commenter who is listed only in the file of the pull request is still authorized, and the reply says so. `AI_BITBUCKET_VERDICT_MIN_ROLE=admin` turns the owners file off. A missing or unreadable file means the old lookup decides. See [Bitbucket setup](docs/bitbucket-setup.md#dismissing-findings).

### Fixed

- **Bitbucket finding numbers are kept across runs (#1065).** Bitbucket keeps one summary comment and rewrites it on every run. The hidden id-map marker held only the findings of the current run. An incremental run that did not report a finding again dropped its `F<n>`, so a waiting verdict command got "F<n> was not found in the current review". A run with no findings restarted the numbering at F1, so a waiting command could apply to a different finding. The marker now keeps earlier entries within a size budget of 4,000 bytes of JSON (about 5.4 KB in the comment). The lowest numbers go first and the highest number always stays. A finding that returns after a run without it keeps its number and no longer gets the "new" badge. A WARNING in the job log shows when earlier entries were dropped. This change affects Bitbucket only.
- **A 403 from the permission lookup gets its own reply (#1068).** The reply used to say "could not verify your repository permissions right now, try again". A 403 does not go away on a retry. The reply now says what to fix: add the commenter to the owners file, add the file, or make the bot account an admin. The command stays pending and applies on the first run after the fix. A command that already has the old reply gets one new reply.

### Changed

- **Container image tool updates (#1061, #1062, #1063).** The image now uses ruff 0.17.1, golangci-lint 2.15.0, and a newer digest of the Ubuntu 26.04 base image.

## [2.23.0] - 2026-10-13

### Added

- **The review now skips before any LLM call when the diff does not fit the model context window (#1056).** `config/model-pricing.json` accepts an optional `context_window` (maximum input tokens) for each model. It is set for Sonnet 5.5, Opus 5.5, and Haiku 5.5, and a model without it is not checked. The engine compares the estimated input tokens plus the output cap of each agent with `AI_CONTEXT_WINDOW_MARGIN` (default `0.9`, `0` turns it off) times that window. A skip comment names the agent, the numbers, and `AI_EXCLUDE_PATTERNS` as the fix for generated files. The check runs without `AI_MAX_COST_USD`. A skip exits 0 by default, and `AI_FAIL_ON_CONTEXT_WINDOW=true` exits 2. The action inputs are `context-window-margin` and `fail-on-context-window`, and rescan and review-full forward both. Behavior change: a diff that used to fail at the provider with "prompt is too long" is now a skip. A provider "prompt is too long" error that gets past the estimate is not yet treated as a skip.

### Changed

- **Behavior change: the token table, the usage line, the high-usage warning and `COST_RECONCILE` now count the pr-summarizer and issue-linker (#1055).** Their usage was missing from every report, so the reported cost was lower than the real spend. The table shows a row for each preflight agent that ran, and the reported cost and the agent count are higher. The `AI_TOKEN_USAGE_WARN_USD` check sees the higher total, so it can fire on a run that did not fire it before.

### Fixed

- **The `COST_RECONCILE` delta no longer prints a wrong negative amount (#1055).** `format_cost` rendered a negative amount through floor division, so a delta of -$0.3070 printed as `$-1.6930`. It now prints `-$0.3070`.

## [2.22.1] - 2026-10-12

### Fixed

- **The review headline now follows a dismissal (#1049).** After a maintainer dismissed a finding, the "Overall Risk | Findings" line kept the old risk and counts until the next full review. Every review body now carries a hidden `headline-map` marker (fingerprint, severity and place of each counted finding). A dismissal removes the finding from it and recomputes the headline, for carried-forward, inline and body-level findings. The marker is the first one dropped when the body is near the size limit. A review posted before this release has no marker, so a dismissed carried-forward finding only lowers the counts and the risk reads `<risk> or lower`.
- **A changed file that resolves outside the workspace is dropped for every analyzer (#1047, item 1).** A symlink, or a file under a symlinked directory, could point at a file elsewhere on the runner. v2.22.0 fixed this for phpcs only. `build_changed_files` now applies the rule once, so no analyzer or agent gets the path.
- **A docs file no longer routes a mixed pull request to no review (#1039).** `when.paths` matches if any one changed file matches, so one `docs/` file next to real code gave the whole PR `agents: []` and `analyzers: []` under this repository's own docs route.

### Added

- **New policy route key `when.paths-all` (#1039).** A route with `paths-all` matches only if every changed file matches at least one of its globs, and never matches an empty file list. `paths` keeps its meaning, so no existing policy file changes. This repository's docs route now uses `paths-all`.

## [2.22.0] - 2026-10-12

### Fixed

- **The phpcs analyzer now honors the repo's own ruleset (#1042).** It applied the Drupal standard to every PHP repo and ignored `phpcs.xml`, so a WordPress plugin got High indentation findings on test files that its ruleset does not lint. The analyzer reads `.phpcs.xml`, `phpcs.xml`, `.phpcs.xml.dist` or `phpcs.xml.dist` as data and gives phpcs a generated ruleset. phpcs never reads the repo file, because a ruleset can load PHP from the workspace (`installed_paths`, `bootstrap`, `autoload`, path-style `rule ref`), which is the same threat as #739. The analyzer keeps the `<file>` scope, the exclude patterns, the rules that name installed standards or sniffs, and their `exclude`, `severity`, `type` and `properties` settings. It rejects a ruleset with a DOCTYPE or ENTITY declaration, a NUL byte, a size over 256 KiB, or a symlink. It applies the `<file>` scope and `type="relative"` exclude patterns itself, because phpcs ignores both for files given on the command line. It matches those patterns without a backtracking regex, so a hostile pattern cannot stall the review. It logs the first five ruleset entries that it drops, then the total. phpcs runs from an empty temporary directory with absolute file paths, and a rule ref or exclude name that is shaped like a file or that exists as a path in the workspace is dropped, because phpcs resolves such a name against its working directory and would load it as a ruleset. A changed file that is a symlink, or sits under a symlinked directory, and resolves to a file outside the workspace is skipped, so phpcs cannot read a file elsewhere on the runner.
- **A merged finding from two different analyzer tools no longer loses the second message (#1044).** When phpcs and phpstan reported nearby lines, the merged finding kept only the highest-severity text, while the badge still named both tools. The merged finding now keeps its own text and lists the other tool's message as `Also reported by:` in the GitHub inline comment, the GitLab discussion, the review body, and the Bitbucket Code Insights annotation. The text is not appended to the finding, because the finding fingerprint hashes it. The roll-up step keeps the notes of every occurrence.

### Changed

- **Behavior change: a PHP repo that is not a Drupal repo no longer gets the Drupal standard.** With no phpcs ruleset, the Drupal and DrupalPractice standards apply only when the repo shows Drupal signals: a `*.info.yml` file, a Drupal 7 `*.info` file with `name` and `core` keys, a `.module`, `.install`, `.theme` or `.profile` file, a composer `type` of `drupal-*`, or a `drupal/core` requirement. Other repos get PSR12 with the docblock sniff. Open pull requests can see new findings and stale threads that resolve.
- **A ruleset that names a standard the image does not have gets a style-neutral fallback.** For example, `WordPress-Extra` is not installed. phpcs then runs seven correctness sniffs with no code-style opinion, plus the repo rules that name installed sniffs, and the log names the missing standard. PSR12 is not the fallback, because it requires spaces and tab-indented code would fail on almost every line. If phpcs rejects the generated ruleset, the analyzer retries once without the repo rules and keeps the repo's top-level exclude patterns.
- **Bugfixes now land directly on `main`.** A defect fix that deserves a patch release no longer goes through a `release/vX.Y.Z` branch. The maintainer cuts the patch release from `main`. Features and other planned changes still use the release branch. This is a process change only, with no engine or workflow code changes. See "Bugfix path" in `CLAUDE.md`.
- **A stale comment in the analyzer bridge is fixed (#1019).** The header of `ai_pr_review/analyzers/bridge.py` said 13 analyzers. It now points at `ANALYZER_NAMES`, so the number cannot go stale.
- **Dependency updates.** Python is 3.15 in the workflows (#1040) and `ruby/setup-ruby` is v1.329.0 (#1041).

### Known limits

- WPCS (the WordPress standard) is not in the image, because WPCS 3.4.1 needs phpcs 3 and `drupal/coder` 9 needs phpcs 4 (#1043).
- Rule-level `type="relative"` exclude patterns are passed to phpcs, which does not apply them to files given on the command line.

## [2.21.0] - 2026-10-09

### Added

- **Each finding now shows where its evidence came from.** A short label and the confidence score appear after the finding text, for example `(corroborated by analyzer, confidence 88)` or `(single agent, unverified, confidence 72)`. The label is one of `corroborated by analyzer`, `analyzer finding`, `judge kept`, `single agent, unverified`, or `single agent, not judged`. The 0 to 100 score is unchanged. It shows on GitHub inline comments and body bullets, GitLab inline discussions and body bullets, and Bitbucket body bullets and Code Insights annotations. It is display text only, and it does not change the approval decision, the finding ids, or the severity and `F` tokens that the comment parsers read. It is on by default. Set `finding-badges: 'false'` (`AI_FINDING_BADGES=false` on Bitbucket) to hide it. A finding the judge gave no usable verdict for (the response left out its id, or the verdict name is not known) shows `single agent, not judged`. `_apply_verdicts()` returns it unchanged, with `judge_verdict` unset, so the finding keeps the same placement as before and the feedback store does not record a verdict the judge never gave. Both cases log a warning.

- **A code-aware judge experiment and a measured comparison are in the eval tools, not in the production review.** `tests/canary/judge_code.py` runs the shipped judge with a short window of the hunk each finding cites (`extract_hunk`), using the prompt `tests/canary/judge_prompts/finding-judge-code.md`. That prompt lets the judge return `unsupported` when the code does not show the problem. The wrapper turns `unsupported` into `downrank` in the model's reply, so the judge still never removes a finding, and corroborated findings stay inline. `findings/judge.py` is unchanged and stays text-only: `judge_findings()` has no `diff_text` parameter, and it treats `unsupported` as an unrecognized verdict. Nothing under `ai_pr_review/` imports the experiment. No setting was added, because the first measurement did not meet the bar to turn it on. `tests/canary/judge_eval.py` replays the saved reviewer responses and compares no judge, the text-only judge, the code-aware judge, and a tweaked text prompt, on Sonnet 5.5 and on Haiku 5.5. On 65 reviewer findings that were read by hand, only the current text-only Sonnet judge separated real findings from the rest (3 of 13 demoted were real, against 32 of 52 kept). The code-aware, Haiku, and tweaked-prompt variants all demoted more real findings, so the shipped judge is unchanged.

- **Behavior change: new analyzer `dep-exists` flags a newly added dependency that its registry does not know.** A model can invent a package name, and an attacker can register that name and ship malicious code under it. For each dependency a diff adds to `package.json`, `requirements*.txt`, `Cargo.toml`, `composer.json`, or `Gemfile`, the analyzer asks the public registry. A name the registry does not know is a High finding on the added line. The analyzer rebuilds the manifest as it was before the change by undoing the diff hunks, and it skips a name that the old manifest already declared as a registry dependency (a version bump, or a move between sections). A name that was a local path, a workspace member, or a git source and now names a registry version is still checked. If the same change touches `.npmrc`, `.yarnrc`, or `.cargo/config`, or moves the manifest, or the old requirements file or Gemfile used a private index or source, every added dependency is checked, because the old names may have come from a private registry. If the hunks do not match the file, every added dependency is checked. An npm, PyPI, or crates.io package first published under 30 days ago is a Medium finding. It sends only the package name. It fails open on a timeout, a rate limit, a redirect (never followed), or any status other than 200 or 404. It skips an ecosystem when the repository sets a private registry, does not check Go modules (a private module would look missing), and checks at most 25 new dependencies per run. Turn it off with `exclude-analyzers: dep-exists`. A High finding makes the review request changes, so a repository can see a pull request blocked by a dependency that is real but private. The analyzer reads only files in the repository, so it cannot see a private registry that is set in CI settings or a user-level config. It also asks the public registry about a private scoped npm package, or about a monorepo package that another package lists by plain version (`workspace:`, `file:` and `link:` specs are skipped). If that affects you, turn the analyzer off with `exclude-analyzers: dep-exists`, or set the registry in a file in the repository. A lookup that gets no usable answer adds no finding, and the run logs one warning with the count of lookups that failed. A `package.json`, `Cargo.toml`, or `composer.json` that cannot be parsed logs a warning and its new dependencies are not checked.

- **The review comment now says what the review did not look at.** A short `Not reviewed:` note lists the file patterns you added with `exclude-patterns`, the agents that did not run because their trigger did not fire, and whether the review is incremental. The note appears in the same part of the comment as the `policy.yml ignored` and cost-ceiling notices, on GitHub, GitLab, and Bitbucket. It is empty when nothing was left out. The built-in lockfile and vendor excludes are not listed because they are the same on every run. It does not change the approval decision, and no new setting was added.

- **Claude Haiku 5.5 has a pricing row, and a model can now have a second set of rates for long prompts.** `config/model-pricing.json` prices `claude-haiku-5-5` (and `claude-haiku-5.5`, with or without a provider prefix) at $0.10 input, $0.50 output, $0.125 cache write, and $0.01 cache read per million tokens for a call whose prompt is up to 100,000 tokens. A call over 100,000 tokens uses the `long_prompt` rates: $0.50, $2.50, $0.625, and $0.05. `ModelRates` has a new optional `long_prompt` field (`LongPromptRates`), and `token_cost_units()` picks the tier from one call's input, cache-write, and cache-read tokens. Each token-log row for an Anthropic model is one call (`agents/dispatch.py` builds the row from a single response, and `llm/anthropic.py` makes one request per call), so the token table tiers each call on its own size. A `long_prompt` object that is present but unusable (no positive threshold, input rate, or output rate) makes the whole model unpriced, with a warning, and does not fall back to the base rates. No other model has a long-prompt tier. This only adds pricing. Haiku 5.5 is not a default, and its `temperature` and effort handling are not set up yet, so a model-change verification run is still needed before it becomes a supported default.
- **`tests/canary/consistency_eval.py` has a hard spend cap and refuses to start without `--yes`.** The harness had no spend limit, and in September 2026 it used about $142 of a $149 six-day quota. ## [2.16.1] - 2026-09-28

### Changed

- **Every third-party GitHub Action in this repo's workflows and in `examples/workflows/` is now pinned to a full commit SHA** with a `# vX.Y.Z` comment (issue #955). A tag can be repointed by a compromised action publisher, and `publish-image.yml` pushes the container image with a write token, so the mutable `@vN` tags were the real exposure. `renovate.json` now extends `helpers:pinGitHubActionDigests` and also covers `examples/workflows/`, so Renovate keeps the SHAs and comments current. The `tag1consulting/ai-pr-review/...@main` self-references are unchanged. Snippets in `docs/` still show `@vN` tags because Renovate cannot maintain them.
- **The `e2e-live` deployment environment gate is removed from the live e2e matrix job.** The environment had no secrets scoped to it and its `release/*` branch policy did not protect against anyone with push access, so it only blocked legitimate on-demand verification of a fix on a non-release branch. The job still runs only for eligible `release/*` PRs and explicit `workflow_dispatch` runs, and `max_cost_usd` still caps spend per run.
- **The weekly credential check can now also be started with `workflow_dispatch`.**
- **The `e2e-gate` check is now a required branch-protection status check on `main`**, alongside the existing AI review and test/lint checks. It was made required after two consecutive green `workflow_dispatch` runs on `main` with verified cleanup.
- **A push to a non-draft `release/*` PR now runs the live e2e legs on that SHA.** Previously a push (`synchronize`) reported a passing `e2e-gate` without running them, so the merged SHA could be unvalidated. A newer push cancels the in-flight run, so only the newest SHA finishes and bills. Draft release PRs and all other PRs still get an immediate pass.
- **`workflow_dispatch` and scheduled runs now report `e2e-gate (manual)`**, so only the automatic PR run reports the required `e2e-gate` context and a manual run can no longer satisfy it. Manual runs use their own concurrency group and cannot cancel a PR run.

### Fixed

- **The `deep-preflight` git clone-auth check no longer fails with "Repository not found" in CI** (issue #962). `git ls-remote` inherited the checked-out repo's working directory, so `actions/checkout`'s local `http.extraheader` for the job's own `GITHUB_TOKEN` was sent alongside the reviewer token's header and GitHub authenticated as the wrong identity. The check now runs isolated from ambient checkout credentials.
- **The e2e verifier no longer reports a false `product_failure` for a finding that overflowed into the review body.** The body-fallback check only ran when a platform's own per-finding surface was empty, so a finding pushed past the inline-comment cap became unverifiable as soon as any other finding filled an inline comment. The fallback is now scoped to individual bullets in the body's "Findings not attached to specific lines" section.
- **`Python (3.14)` no longer gets stuck at "Expected" on PRs that touch no Python files.** `lint.yml` had a `paths:` filter on its `pull_request` trigger, so docs-only and workflow-only PRs never started the workflow and the required check never reported. The filter is removed from the `pull_request` trigger.

## [2.15.0] - 2026-09-25

### Added

- **A deterministic Python e2e test harness (`tests/e2e/`), replacing the old ~815-line LLM-orchestrated e2e script**. It opens throwaway PRs/MRs on the real GitHub/GitLab/Bitbucket test repos, runs the built review container against them, and verifies the posted output with plain code (telemetry JSON, fetched comments/annotations) instead of asking an LLM to eyeball shell output. A new `.github/workflows/e2e.yml` builds the candidate image once and runs it against all three platforms in parallel matrix legs, gated behind an `e2e-gate` aggregate check and a dedicated `e2e-live` GitHub Environment restricted to `release/*` branches. Live-run end to end against all three platforms at least once each, including together in a single 3-platform `workflow_dispatch` run: GitLab and Bitbucket each passed cleanly; GitHub's runs correctly exercise every check but do not currently pass cleanly, because the seeder and reviewer identities are the same personal token (see the Known limitation entry below) -- not a harness malfunction, but a real, current gap. Unit tests for the harness's pure verification logic live in `tests/python/e2e_harness/` (65 tests, no network, no cost) and run as part of the normal test suite.
- **`.github/workflows/lint.yml`'s test/lint job is now a required branch-protection status check on `main`**, alongside the existing AI review check. It already ran on every PR; it just wasn't required, so a PR with failing tests, ruff, or mypy could previously still merge.

### Fixed

Found and fixed during this harness's own live validation runs and a follow-up comprehensive review, before any of it shipped:

- Per-platform pinned fixture seed SHAs (GitHub, GitLab, and Bitbucket are independent repositories with genuinely different commit hashes for "the same" content — a single shared seed SHA 404'd on GitLab).
- The self-approval-degrade check now compares the posted event against telemetry's own stated intent instead of a hardcoded `expected_event="APPROVE"`, which produced a false failure on a legitimate `REQUEST_CHANGES` outcome.
- Bitbucket auth scheme (git-over-HTTPS requires the fixed username `x-bitbucket-api-token-auth`, not the account email), URL-encoding of account emails embedded in clone URLs, and Code Insights annotation pagination (Bitbucket's own `next` link for that endpoint is malformed and 404s on page 2; the harness now paginates itself against a known-correct URL, terminated by the response's own `size` field).
- The `e2e-gate` check could report success on a release PR whose own eligibility checks (ruff/mypy/pytest) were failing, because the gate never checked `needs.eligibility.result` before its `is_release` branch — confirmed independently by three review agents before it could ship.
- Reviewer-token and Anthropic-key env var fallbacks (`.get(A, .get(B, ""))`) didn't fall back when GitHub Actions sets an unconfigured optional secret to an empty string rather than leaving it absent.
- Git clone credentials are now passed via `GIT_CONFIG_*` environment variables (an `http.extraHeader` Basic-auth header) instead of embedded in the clone URL, removing them from process argv (`/proc/<pid>/cmdline`, `ps`) and from the cloned workspace's `.git/config`.
- The harness's own output directory was created world-writable (`0o777`); now `0o1733` (sticky bit), the standard mitigation against another local user tampering with files they don't own.
- Non-idempotent resource-creation POSTs (branch/ref creation, commit creation, opening a PR/MR) no longer retry on a timeout or 5xx, which could otherwise create a duplicate resource if the original request had actually succeeded server-side.
- Bitbucket's adapter now cleans up an orphaned branch on a failed `create_run_commit`/`open_pr`, matching GitHub and GitLab's existing behavior (previously only they had this).
- `ExpectedFinding` matching in `verify.py` no longer treats a platform's entire summary comment as one substring-matchable string; it now matches within each individually-scoped finding (an inline comment, or a Bitbucket annotation's own fields) so an unrelated finding elsewhere in the same summary can't coincidentally satisfy a different finding's expected path/category pair.
- Four hand-copied, inconsistently-bounded pagination loops across the GitHub and GitLab adapters, plus two on Bitbucket, are consolidated into two shared helpers with one consistent page cap and truncation signal.
- CI artifacts (`*.container.log`, `telemetry.json`) now get a literal-value secret redaction pass on top of the existing pattern-based redaction, guarding against a real secret value that doesn't happen to appear in a recognizable `Bearer`/`Basic`/token-labeled shape.
- `run-local.sh` now builds a local candidate image from the invoking checkout instead of defaulting to the mutable, published `:dev` tag, and fixed its `glab auth status` token extraction (missing `--show-token`, which was capturing the masked placeholder instead of a usable token).
- The `verify.py`/`platforms.py` data-shape classes (`RawEvidence`, `RunCommit`, `PullRequest`, `AdapterError`) moved into a new `models.py` with no I/O imports, so `verify.py`'s "pure, no I/O" claim no longer depends on merely not calling into the I/O-performing `platforms.py` — it no longer imports that module at all.

### Known limitation

- **GitHub's e2e leg runs self-review-degraded**: the seeder and reviewer identities are currently the same personal token (no second GitHub identity has been provisioned yet), so GitHub downgrades an intended `REQUEST_CHANGES`/`APPROVE` to a plain `COMMENT` — a real platform restriction the harness correctly detects and fails on, not a harness bug. `e2e-gate` is not yet a required branch-protection check on `main`; it becomes required only after two consecutive green `workflow_dispatch` runs with verified cleanup, a separate future step.

## [2.13.0] - 2026-09-24

### Added

- **Bitbucket reaches feature parity with GitHub/GitLab for finding lifecycle management (issues #839, #873, #874)**. Three phases, previously shipped with no CHANGELOG coverage:
  - **Cross-run dedup (#839)**: Bitbucket previously reposted every finding on every run. `post_findings` now calls the same `_canonical.classify()` decision table GitHub and GitLab use (`all_threads=[]`, since Bitbucket has no comment threads at all), so only `new`/`recurred`/`suppressed` are reachable and an unchanged finding is no longer reposted.
  - **Code Insights annotations (#873)**: findings are now also rendered as a Bitbucket Cloud Code Insights report (`ai_pr_review/vcs/_code_insights.py`), giving inline diff-anchored annotations the way GitHub/GitLab inline comments do — Bitbucket has no repliable inline-comment API, so this is the closest available equivalent. The report is deleted and rebuilt every run (so a fixed/suppressed finding drops out with no extra tracking) and each annotation carries the same `[F<n>]` token as the summary comment. Gated by the `AI_BITBUCKET_CODE_INSIGHTS` repository variable, **default `true`**.
  - **Verdict-command polling (#874)**: Bitbucket Pipelines has no comment-triggered event, so `/ai-pr-review dismiss|false-positive|wont-fix|fixed F<n>` commands can't be applied the moment they're posted the way GitHub/GitLab slash commands are. `ai_pr_review/vcs/_bitbucket_verdicts.py` instead polls the PR's own comment log for these commands at the start of the *next* review run and applies them then, always as a body-level (never inline-reply) verdict. Authorization is fail-closed by design — a permission-lookup failure rejects the command outright rather than accepting it, the one place in the Bitbucket-parity work where fail-soft was deliberately not used, since the motivating case was a commenter trying to silence a real secret-scanner finding. Gated by the `AI_BITBUCKET_VERDICTS` repository variable, **default `false`** (opt-in, unlike Code Insights — an unset/empty/typo'd value resolves to off rather than silently enabling a security-relevant feature). Minimum commenter permission required is set by `AI_BITBUCKET_VERDICT_MIN_ROLE` (`read`/`write`/`admin`), default `write`.
  - All three build on the fingerprint/authorship hardening in the #886/#887/#894 entries below, found during this same body of work's own security-review passes.
- **Further Bitbucket parity: findings visibility, fail-on-findings default, real reviewer state (issues #917, #918, #920)**. Surfaced by live-verifying the Bitbucket-parity work above against a real Pipelines run:
  - **Code Insights annotated findings are no longer invisible in the review comment (#920)**: previously, a finding that landed a Code Insights annotation was excluded entirely from the summary comment's rendered findings list, leaving only a bare count with no severity/description/remediation text anywhere in the comment — Bitbucket's annotations only render in the Diff view or a separate Reports tab, far less discoverable than GitHub/GitLab's real inline comment threads. Every active finding now renders as a bullet in the comment regardless of annotation status; one that also got an annotation gets a shortened bullet (no remediation, since that detail already lives on the diff).
  - **`AI_FAIL_ON_FINDINGS` now defaults to `true` in the Bitbucket starter pipeline (#917)**: the example `bitbucket-pipelines.yml` never set this variable, so the pipeline step exited 0 even when the review decided `REQUEST_CHANGES` on Critical/High findings — now matches the GitHub Action example's own fail-closed default.
  - **The decided review outcome now has a real effect on Bitbucket's own reviewer-state UI (#918)**: `REQUEST_CHANGES`/`APPROVE` previously only changed heading text in the summary comment; no call was ever made to Bitbucket's actual approve/request-changes endpoints, so the PR's reviewer-state badge (and any branch-restriction rule keyed off "changes requested") never reflected the review's real decision. `BitbucketProvider._set_review_state` now calls those endpoints after the summary comment PUT succeeds — `APPROVE` clears any prior request-changes state then approves, `REQUEST_CHANGES` clears any prior approval then requests changes, `COMMENT` clears both (the downgrade case). Fail-soft throughout, gated by a new opt-out `AI_BITBUCKET_REVIEW_STATE` repository variable, **default `true`**. **Behavior change**: since this defaults on, a repo upgrading into this release starts getting real approve/request-changes state on Bitbucket immediately with no opt-in step — the bot's `APPROVE` can now satisfy a branch-restriction rule that counts approvals, and its `REQUEST_CHANGES` can now block a merge, where neither did before. Set `AI_BITBUCKET_REVIEW_STATE=false` to keep the prior heading-text-only behavior, and review your branch restrictions before upgrading if they count bot approvals toward a merge requirement.
    - **Follow-up fix, same feature**: the first cut of `_set_review_state` sent a bodiless POST, which Bitbucket's `/approve`/`/request-changes` endpoints reject with a bare-text `400 Bad Request` when combined with this client's default `Content-Type: application/json` header — live-verified against a real Bitbucket PR while running the `ai-pr-review-e2e` workflow ahead of this release. Fixed by sending an explicit `{}` body; the endpoints ignore body content entirely (participant state comes from the authenticated user + URL alone), so this only exists to make the `Content-Type` header honest. Live-verified fixed against the same PR before merge.
- **`approval-ceiling` input / `AI_APPROVAL_CEILING` env var (issue #858)**: caps the strongest review event this bot may post. `approve` (default): unchanged behavior. `request-changes`: a clean/Low/Medium outcome posts `COMMENT` instead of `APPROVE`; `Critical`/`High` still post `REQUEST_CHANGES`. `comment`: every outcome posts `COMMENT`, so the bot never sets a formal review state and a human makes every merge decision. `AI_FAIL_ON_FINDINGS`'s exit code is unaffected by this setting — a clean PR still exits 0, a Critical/High-finding PR still exits 2, regardless of the ceiling; use `fail-on-findings` plus a required status check as the merge gate when a non-`approve` ceiling is set, since branch protection can no longer require this bot's own approval. A non-`approve` ceiling also disables the `/ai-pr-review dismiss` auto-approve-on-dismiss escalation (issue #590). On GitLab, which never posts a real approval state, this only changes rendered review text; on Bitbucket, the same capped outcome also drives the real approve/request-changes calls `_set_review_state` (issue #918, above) makes, so the ceiling caps that too. Deliberately not `policy.yml`-configurable — see [Configuration: Approval ceiling](docs/configuration.md#approval-ceiling).

- **Verdicts marker forgeable via unsanitized pr-summarizer/issue-linker output (issue #886)**. `sanitize_display_text` (`vcs/_body.py`) was only ever applied to `finding`/`remediation` text and (partially) to the pr-summarizer walkthrough table — never to the full carried-forward summary/issue-linker output, which is read back verbatim by `marker.py`'s `extract_verdicts`/`extract_id_map`/`extract_summary_sha` on every subsequent run. Pre-existing on GitHub, GitLab, and Bitbucket alike; not introduced by the recent Bitbucket-parity work, which is where it was found (a security-reviewer pass during Phase 3).
  - **Follow-up hardening, same issue**: the first fix above defanged only the single literal spelling `"[//]: # ("`, but every hidden-marker regex in `marker.py` tolerates optional spaces/tabs around the `#` (a real Markdown link-reference-definition rule renderers honor), so a spacing variant like `"[//]:#("` survived it and still parsed as a real marker. The sanitizer's defang now derives from the same shared `HIDDEN_MARKER_OPENER_RE` pattern every hidden-form extractor builds from, so the two can't drift apart again. Separately, `upsert_verdicts_marker` patched only the *first* same-form marker match (`.search()`) while `extract_verdicts` reads the *last* — a forged marker-shaped string earlier in a body (from either gap above) could silently absorb a slash-command's real verdict write, orphaning it behind the still-untouched genuine marker; upsert now also takes the last match per form. Bitbucket's `_extract_walkthrough` carries prior summary-comment text forward verbatim into every later run's `### Summary` section without re-sanitizing it, so a forged marker embedded before either fix above shipped (or surviving in a body an incremental run never re-renders) stayed live indefinitely; it's now re-sanitized on every extraction. Finally, GitHub reviews with no recorded verdicts, and Bitbucket summary comments with `AI_BITBUCKET_VERDICTS` off, previously omitted the verdicts marker entirely — since `extract_verdicts` trusts whichever marker-shaped string sorts last in the body, a body with no real marker at all let any forged one elsewhere win by default. - **`fingerprint()` delimiter collision (issue #887)**. `vcs/_finding_ids.py`'s fingerprint joined `source|file|line|text_hash` with a bare `|` and no escaping; `source`/`file` are agent-supplied strings that may legitimately (or via prompt injection) contain a literal `|`, so two distinct findings — e.g. `source="a|b", file="c"` vs. `source="a", file="b|c"` — could produce an identical fingerprint string. Following the "warn, don't suppress" direction the issue itself recommended (silently treating a resolved-unverdicted thread as suppressed forever would repeat the exact silent-data-loss mistake `#771`/ADR 0003 just reasoned through and rejected for a different mechanism): a new `find_resolved_match()` in `_canonical.py` lets GitHub's `post_findings` detect this specific case — via exact fingerprint match only, not the fuzzy location match `classify()` uses elsewhere, so this can only ever add an explanatory note to a comment that was posting either way, never change what gets suppressed. Critically, it also checks GraphQL's `resolvedBy` field and fires only when a human (not this bot) did the resolving: `resolve_stale()`'s own routine housekeeping resolves any unresolved bot-owned thread whose finding didn't reappear in a given run, on every successful run, producing the identical resolved-with-no-verdict shape for a completely unrelated reason — without this check, the note would misattribute the bot's own cleanup to a human decision that never happened. The freshly posted inline comment or body bullet now says the finding was previously resolved without a verdict and names the commands (`dismiss`/`false-positive`/`wont-fix`) that would suppress it for good. `classify()` itself, and GitLab's identical call into it, are completely unchanged — GitLab has no verdict system, so this check would misfire as noise for every resolved discussion there, and is deliberately kept GitHub-only rather than gated inside the shared, platform-agnostic classification module.
- **GitHub: `dismiss`/`false-positive`/`wont-fix`/`fixed` verdicts could be silently discarded whenever the canonical review being patched was also the one that first rendered the finding — the common case, not an edge case (issue #771)** — the `#755` self-consistency guard treated a fingerprint present in a review's own id-map, co-occurring with that same body's verdicts marker claiming `dismissed`/`fixed` for it, as corruption. That shape is also exactly what a legitimate slash-command dismissal produces, since `_record_verdict` PATCHes a verdict onto an already-rendered review without touching its id-map, by design. The guard couldn't distinguish the two, so a real dismissal evaporated on the next read whenever it hit this shape. Removed the read-time guard (`_canonical.merge_verdicts`); the construction-time guard in `github.py` (which only ever inspects a run's own about-to-be-posted output, so it can't be confused by a later human patch) remains as the sole automated defense against the original `#755` symptom on the render path — it does not cover the suppression path (`classify()`'s exact/fuzzy `dismissed` match), which now carries an `INFO`-level log naming the fingerprint at the point of suppression instead of any guard, an accepted residual risk given `#755`'s trigger was never reproduced. The now-passive read-time log was downgraded to `INFO` (from the removed guard's `ERROR`) since it fires on this same routine, correct-dismissal shape on every run, not just a hypothetical corruption. No backfill needed — the guard never rewrote persisted review bodies, only discarded verdicts from an in-memory recomputation, so every already-affected PR self-heals on its next review run. See `docs/adr/0003-single-guard-against-self-contradictory-verdicts.md` for the full reasoning, including a review-panel finding that caught the suppression-path gap in the first draft of this fix.
- **A `/ai-pr-review wont-fix`/`false-positive`/`dismiss` slash command posted two bot replies and, for a body-level finding, two identical feedback-store entries (issue #769)**. `slash-commands.yml`'s `dismiss-body-finding`/`dismiss-finding` jobs and its `feedback-command` job both fired for the same comment — neither `needs:` the other — so both acted and both posted. Live-verified on PR #768: two `wont-fix` comments each produced a duplicate reply and, per `learnings.jsonl` on the `ai-pr-review-bot` branch, a duplicate store entry. `dismiss-body-finding`/`dismiss-finding` are now the sole owner of the reply and the feedback-store write for the whole verdict family (`dismiss`/`false-positive`/`wont-fix`/`fixed`), on both `issue_comment` and `pull_request_review_comment` events; `feedback-command` no longer handles these commands at all. This also upgrades a case that was silently losing signal before: a top-level comment naming an `F<n>` that classifies as an **inline** finding now gets a full-context feedback-store entry (source/file/rule_id from the thread itself, no extra API call) instead of the empty-context entry `feedback-command` used to write for it, and `dismiss-inline` (inline review-thread replies) can now write to the feedback store at all — it never did before. A store-level dedup guard was also added as defense-in-depth, scoped to `false-positive`/`wont-fix` only: two writes for the same verdict within a 10-minute window are now skipped (loudly — a `WARNING`/`::warning::`, not silent) rather than both landing. The dedup identity includes the finding's `F<n>` id (now threaded through `dismiss-inline`, which never persisted one before this PR) specifically so two *different* findings dismissed close together don't collide on the same key. **Behavior change for every consumer of this reusable workflow**: a `COLLABORATOR`'s (not `OWNER`/`MEMBER`) top-level `wont-fix`/`false-positive` verdict is no longer persisted to the learning store — this closes a pre-existing gap where `dismiss-body-finding` admitted `COLLABORATOR` and forwarded `AI_FEEDBACK_LOOP` unconditionally, contradicting the documented OWNER/MEMBER-only policy (`docs/learning-loop.md`). Also fixed as a side effect of this refactor: a successful `fixed` on a body-level finding previously reacted `::notice::reaction=confused` (nothing to derive `acted` from in the old expression) despite the command succeeding; it now correctly reacts `done`.
- **GitHub: a run with no new findings but a still-open bot-owned thread from an earlier run could post a review headline claiming a nonzero finding count with nothing anywhere in the body to back it (issue #766)** — e.g. `Findings: 1 (0 inline)` with no finding text, no link, and an empty id-map. `post_findings` synthesizes a stub for every unresolved thread this run's classification pass didn't touch so the headline count/risk reflect the PR's true current state, but that stub was never rendered and was excluded from the inline count. The review body now includes a "Still open from earlier reviews" section (severity, F-ID when known, `path:line`, and a permalink to the thread) whenever such a thread exists, and the inline count includes it. Separately, a still-open Critical/High thread now forces a would-be `APPROVE` down to `COMMENT` instead — on GitHub a newer `APPROVE` from the same reviewer supersedes an older `CHANGES_REQUESTED` review, so posting one over a known-unresolved Critical/High finding would have silently unblocked a PR that should stay blocked. GitHub-only; GitLab and Bitbucket have no canonical-review-reuse mechanism to carry a thread forward from.
- **GitHub: a `recurred`-with-thread finding could also inflate the headline count with nothing counted as backing it (issue #767)** — the adjacent case #766's fix didn't cover, found during that fix's own review. A `recurred` classification with `c.thread is not None` (an existing thread previously verdicted `fixed`/`dismissed`, then reopened because the same finding came back) is folded into `headline_findings` (counts toward `finding_total`), but was never added to `headline_inline_count` — producing the identical `Findings: 1 (0 inline)`-shaped contradiction #766 fixed for carried-forward threads, via a different classification path. Less severe than #766's case in practice, since a `recurred` finding does get a live, fresh reply posted on its existing thread this run (`_notify_recurrence`) — a human watching the PR's activity feed would see it — but the headline count itself was still wrong. `headline_inline_count` now also counts `recurred`-with-thread findings, matching how `update`/`escalate` findings already count (they're the same shape: a live inline comment this run touched, just not re-rendered in the body). A body-level `recurred` (`c.thread is None`, nothing to reopen) is unaffected — it already renders in `body_findings_text` and correctly counts as a body finding.

- `GitLabProvider.resolve_stale()` had no concept of "a discussion this same run just created or matched as still active" — it resolved every owned, unresolved, resolvable, marker-bearing discussion on the MR unconditionally, including one `post_findings` had just posted moments earlier in the same run (`orchestrate.py` calls `resolve_stale()` immediately after `post_findings()`). In effect, every GitLab inline review comment was auto-collapsed as "resolved" before a human ever saw it as open — the same bug class already fixed once on GitHub (issue #718), reintroduced on GitLab from day one. Fixed with the same per-run keep-alive tracking GitHub uses; applies regardless of `AI_GITLAB_CROSS_RUN_DEDUP`.
- `GitLabProvider.post_findings`'s failure detection compared `inline_posted == 0` against `len(findings) > 0`, which would misclassify a run with zero inline candidates (everything routed to the body, or everything matched an existing discussion) as a failure. Now compares against `len(inline_candidates)` (what was actually attempted) and requires a real HTTP error, not just "nothing needed posting."
- `/ai-pr-review dismiss`, `false-positive`, and `wont-fix` on a body-level finding could reply with a raw `::warning::` GitHub Actions annotation glued onto the front of the posted PR comment. - A finding's stable `F<n>` ID could be misclassified as body-level, never resolving its thread or dismissing the blocking review, if an older review had once rendered it as an out-of-diff body bullet before it moved to an inline thread in a later run. Classification now prefers the newest review that renders the ID at all, so a finding that has moved buckets between cycles is resolved correctly. ## [2.7.0] - 2026-09-02

### Added

- **Canonical-review reuse (GitHub)**: rerunning the review no longer always posts a new review object. A fully quiet rerun updates the existing review's body in place; a still-open finding is updated (with a reply on severity escalation) rather than reposted; a `fixed` finding that recurs gets a reply and its thread reopened; a `dismiss`/`false-positive`/`wont-fix`'d finding is never reposted, even a fuzzy-matched nearby one of a compatible category and no higher severity. Only a genuinely new finding — or one severe enough (High/Critical) to require visibility regardless of diff anchoring — triggers a fresh review, and the prior blocking review is dismissed only after the fresh review is confirmed to have actually posted. Set `AI_CANONICAL_REUSE=false` to disable. See [docs/features.md](docs/features.md#quiet-reruns-github). GitHub-only; GitLab/Bitbucket parity tracked in issue #710.
- `GITHUB_BOT_USERNAME`: override the login GitHub-side review-selection and thread-ownership checks treat as "this bot's own", mirroring the existing `GITLAB_BOT_USERNAME`. Needed by any consumer whose reviews post under a non-default identity (a custom GitHub App, or a personal-access-token-authenticated account, as in this project's own e2e test harness) — without it, canonical-review reuse's review-level PUT-in-place path can never find a prior review to reuse, confirmed live against a real test PR.

### Fixed

- A top-level PR comment carrying several `/ai-pr-review dismiss`/`false-positive`/`wont-fix`/`fixed`/`feedback` lines only ever acted on the first line; the rest were silently ignored. Both the `dismiss-body-finding` and `feedback-command` workflow jobs now scan every qualifying line in the comment and reply once with a combined result (issue #733).
- The review body's inline-ownership marker was appended after the byte-truncation step with no size reserve of its own, letting a rendered GitHub review body exceed the provider's 65,536-byte limit by the marker's length. The truncation reserve now accounts for the inline-ownership, id-map, and verdicts markers together.
- `_record_verdict` (the `/ai-pr-review dismiss`/`false-positive`/`wont-fix`/`fixed` verdict-recording path) now seeds its verdicts map from every prior bot review, not just the canonical review's own body — a marker-less review becoming canonical (e.g. the PR-wide auto-approve path's human-facing message) could previously erase every earlier verdict the next time one was recorded.
- Canonical-review reuse's thread-ownership check compared GitHub's GraphQL-reported author login (`"github-actions"`) against a REST-style constant (`"github-actions[bot]"`), rejecting every real thread and making the entire reuse feature a no-op in production while also defeating its own dismiss-safety gate. `resolve_stale` and `_dismiss_stale_reviews` had the same pre-existing bug, independent of and predating canonical-review reuse. Fixed everywhere by normalizing the REST-style constant before comparison (`ai_pr_review.vcs._stale.graphql_bot_login()`), which restores the author check as a real defense-in-depth signal instead of dropping it (issue #717).
- Fixing #717 made `resolve_stale` recognize real threads again, which would have immediately undone canonical-review reuse's own thread keep-alive: it would re-resolve a thread `post_findings` had just PATCHed (`update`/`escalate`) or reopened (`recurred`) in the same run. `post_findings` now records the thread ids it touched each run (`GitHubProvider._kept_alive_thread_ids`) and `resolve_stale` skips them (issue #718).
- Bitbucket's rendered review comment embedded the token-usage table inside the same string that gets truncated at the 32,000-byte limit, so it could be silently cut off — including the model name, which the `ai-pr-review-e2e` canary checks for. An initial fix reordered the table ahead of the (often large) PR walkthrough, but a live e2e run against a heavily-seeded test PR (63 findings) showed that findings alone can exceed the whole byte budget with no walkthrough involved, so ordering alone doesn't guarantee survival. The table's bytes are now reserved and it is appended after truncation instead, the same way the id-map marker already was (issue #728).

### Security

- **Fork PR checkout (#738) reopened a code-execution path in three native analyzers.** `ai-review.yml`'s `pull_request_target` workflow now checks out untrusted fork-PR content inside a container holding `ANTHROPIC_API_KEY` and a `GITHUB_TOKEN` with `pull-requests:write`/`checks:write`. `phpstan`, `checkov`, and `tflint` all auto-discovered and executed config/plugin content from that workspace (`phpstan.neon`'s `bootstrapFiles`/`includes`, `.checkov.yaml`'s `external-checks-dir`, `.tflint.hcl`'s `plugin_dir` plus the `./.tflint.d/plugins` fallback) — the same class of bug fixed for `eslint` in #738. All three now run against a freshly created, empty, trusted config file passed via an explicit CLI flag (which always wins over each tool's own auto-discovery), and `tflint` additionally pins `TFLINT_PLUGIN_DIR` to a fresh empty directory. This is an unconditional behavior change, not limited to fork PRs: a project's own `phpstan.neon`/`phpstan.neon.dist` is no longer honored (`PHPSTAN_LEVEL` always applies now); `phpstan`'s Drupal-aware autoloading now only ever uses the image-baked `/opt/composer` install, never a workspace `vendor/` tree. The `sarif-prep` workflow job also now clears `sarif-results/` before running its analyzers, and the `review` job clears it again before downloading the real artifact, closing a related path where a fork-committed SARIF file could survive as a confidence-90 corroborating finding if the genuine tool failed to produce output (issue #739).
- `resolve_stale` had no way to know which threads `post_findings` had just deliberately kept alive (PATCHed for an `update`/`escalate` classification, or reopened for a `recurred` one) in the same run — fixing the bot-login issue above would have made it immediately re-resolve those threads, undoing canonical-review reuse's entire point. `post_findings` now records the threads it touched and `resolve_stale` skips them (issue #718).
- The superseded canonical review could be dismissed before confirming the replacement review actually posted, and an incomplete/failed thread fetch was treated as "nothing unresolved" — both could leave a PR silently unblocked on a mid-run failure. The dismissal now runs only after a confirmed, non-degraded post, gated on a complete thread fetch.
- Two findings that both fuzzy-matched the same open thread in one run could double-`PATCH` the same comment (silently dropping one) or double-post an escalation reply; only the highest-severity match per thread is now kept.
- A failed comment update was still counted as successful and still triggered an escalation reply claiming a change that didn't land.
- A thread reopened by a recurrence reply could still be dismissed alongside its review in the same run, because the dismiss-safety check read a snapshot taken before the reopen.
- `_try_put_canonical` returning early because a newer run's push had already advanced the PR's head was indistinguishable from an actual write, which could let the SHA watermark advance to a stale commit. `FindingsResult` now carries a `skipped` flag and `orchestrate.py` no longer advances the watermark when it's set.
- A finding that fuzzy-matched an open thread as an `update` kept the thread's visible `**[F<n>]**` token, but the reworded finding's own fingerprint (which can differ from the thread's, since the fuzzy match tolerates a few lines of drift and reworded text) got baked into the comment's private metadata marker and minted a second, never-rendered id in the review body's id-map. A human dismissing that thread while it still showed the old fingerprint could have their verdict silently stop applying on the next run, once the thread's marker moved on, because the exact-fingerprint check missed and the fuzzy-dismissed fallback couldn't find the thread anymore either, so the dismissed finding reposted as new. The thread's comment marker now carries every fingerprint it has ever shown (capped at 20 entries), and the id-map reuses the thread's existing id instead of minting a new one, so a dismiss recorded at any point in a finding's drift history keeps suppressing it. (#720)
- Canonical-review reuse's `decide_action` forced a fresh review on every single rerun for any PR with a persistent out-of-diff High/Critical finding, or with more inline-eligible findings than `max-inline` allows — exactly the noisiest PRs the feature exists to quiet down. A finding whose exact fingerprint is already visible in a prior review body no longer forces a fresh review on its own, and `any_new_inline_eligible` is now computed from which findings actually landed an inline comment rather than raw eligibility.

### Changed

- `GitHubProvider.list_bot_reviews()` and `_list_prior_bot_reviews()` (the write- and read-side sources feeding canonical-review selection) now share a single paginated walk over `GET /pulls/{n}/reviews` (`_list_reviews_paginated`), parameterized by an error-handling `strict` flag and an optional state filter. The two independently hand-written walks had drifted into inconsistent contracts; sharing the pagination and bot-login-filtering mechanics removes the risk of them drifting further apart from an ordinary implementation bug. The two contracts remain deliberately different (see `docs/architecture-internals.md#canonical-review-reuse-github`) — no observable behavior changed for either method's callers.

## [2.5.0] - 2026-08-27

### Upgrading

If you already have `.github/workflows/ai-review.yml` (or equivalent) set up from before this release and want to use `policy.yml`'s `head-branch` route matching (e.g. routing by `release/*`, `feature/*`, etc.), you need to add the `head-ref` action input to your workflow — it is not wired automatically just by upgrading the action version:

```yaml
- uses: tag1consulting/ai-pr-review/container-action@main
  with:
    head-ref: ${{ github.event.pull_request.head.ref }}
    # ...your existing inputs
```

Without it, `when.head-branch` routes in `.github/ai-pr-review/policy.yml` never match — the action has no way to know the PR's head branch name — and matching PRs silently fall through to the next route or the `default` policy instead of erroring. `paths` and `base-branch` routes are unaffected; they work without `head-ref`.

The shipped GitHub, GitLab, and Bitbucket templates (`examples/workflows/pr-review.yml`, `examples/pipelines/.gitlab-ci.yml`, `examples/pipelines/bitbucket-pipelines.yml`) already wire this for new installs. This only matters if you copied your workflow from an older version of a template and haven't re-synced it since.

### Added

- **`.github/ai-pr-review/policy.yml`: repo-local review-policy routing.** Route review depth (which agents/analyzers run, quick vs. full mode) by changed-file path, base-branch glob, or head-branch glob, instead of hand-rolling a GitHub Actions expression per repo. Named policies (`agents`/`exclude-agents`/`analyzers`/`exclude-analyzers`) extend a built-in base (`quick`, `full`) or another named policy; an ordered `routes` list matches on `paths`/`base-branch`/`head-branch`, falling back to a configurable `default`. Fully opt-in and fail-soft: a repo with no `policy.yml` sees no behavior change at all, and a malformed file prints one warning and falls back to the engine's hard-coded defaults rather than blocking the review. Loaded from the PR's *base* ref, never the PR head, so a PR can't weaken its own review by editing its own policy file. Requires the `head-ref` action input (now wired into all three provider templates) for `head-branch` routes — see Upgrading above. See [docs/policy.md](docs/policy.md). (#663, #664)
- **Merge gate**: a route's `require` field names a policy that must have (at least) run before merge. An automatic push satisfying only a cheaper tier posts an `action_required` `ai-pr-review/policy-gate` check instructing the reviewer to run `/ai-pr-review review-full` (or add the `ai-review-full` label); once a run at the required tier lands for that commit, the check flips to `success`. Add branch protection requiring that check to make it a real gate. GitHub only for now — a no-op on GitLab/Bitbucket. (#665, #672)
- This repo now dogfoods the feature: docs-only PRs route to a near-zero-cost tier, and `release/*` branches require a manually-triggered full review before merge. (#671)

### Changed

- Ported two small wording improvements from `claude-comprehensive-review`'s equivalent prompts to close drift found during a parity audit: `architecture-reviewer` gained a goroutine/thread-lifetime and resource-cleanup bullet under Scalability and Performance, and its Maintainability bullet now specifies invariants should be "documented with comments"; `edge-case-hunter`'s PHP loose-comparisons bullet now specifies "across types". (#669)

### Fixed

- **`policy.yml`'s `agents: []` / `analyzers: []` (the near-zero-cost tier's intended shape) silently permitted every agent/analyzer to run instead of suppressing them all**, discovered live on a docs-only PR that unexpectedly posted a full review. Fixed in `_merge_allowlist()`. (#674, #677)
- **`ai-review.yml`'s hardcoded `review-mode` fallback always won over `policy.yml` routing**, so a repo relying on policy-file routing alone never saw its routes take effect. The shipped template now defers to policy resolution instead of a hardcoded `'quick'` default. (#675, #676)
- **Preflight agents (`pr-summarizer`, `issue-linker`) were caught by a restrictive policy's `agents: []` deny-all**, even though they describe the PR rather than review its code — a docs-only PR routed to the content tier posted zero findings *and* no PR summary at all. These two separately-dispatched agents are now exempt from policy-driven deny-all; an explicit `exclude-agents` entry naming one of them still suppresses it. (#683, #684)
- **The slash-commands reusable workflow's explicit `permissions:` block capped every unlisted scope to none for every caller, regardless of what the caller granted** — including `checks: write`, needed to (re-)post the merge-gate's `ai-pr-review/policy-gate` check from a `/ai-pr-review review-full` run. GitHub Actions reusable-workflow semantics: any explicit `permissions:` block on `workflow_call` caps all unlisted scopes to none, even when the caller grants more. The block is now removed entirely so the workflow inherits the caller's grants — superseding an earlier, narrower attempt that only dropped `checks: write` from the block's own scope list. **Upgrade note:** the reusable workflow itself no longer caps any scope, so a caller with no explicit `permissions:` block of its own now runs `slash-commands.yml` with whatever default `GITHUB_TOKEN` permissions the repo/org has configured (read/write-all on older repos), not the previously-capped set. Declare an explicit least-privilege `permissions:` block in your own calling workflow — see the shipped [`examples/workflows/comment-triggers.yml`](https://github.com/tag1consulting/ai-pr-review/blob/main/examples/workflows/comment-triggers.yml) template. (#678, #679, #686, #687)
- **The merge gate's unmet-requirement check posted a `neutral` conclusion, which GitHub's required-status-check rules treat as satisfying the requirement exactly like `success`** — so branch protection requiring `ai-pr-review/policy-gate` never actually blocked a merge; the gate was advisory only. Caught during v2.5.0 release-prep review (before this behavior shipped to any tagged release). Now posts `action_required` instead, which is excluded from GitHub's pass set (`success`/`neutral`/`skipped`) and genuinely blocks merge until the required tier runs. (#688)
- Duplicate/contradictory "Related Issues & PRs" heading in `pr-summarizer` output. (#670)

## [2.4.9] - 2026-08-24

### Security

- **`<repo-feedback>` entry attributes are now HTML-escaped before injection into the agent system prompt.** `ai_pr_review/feedback/inject.py`'s entry template previously used Python's `repr()` to render `command`/`source`/`file`, with no escaping. `file` is derived from the PR's own diff/path and carries no upstream sanitization (unlike `reason`, which `_sanitize_reason` already escapes). Because `repr()` switches to double-quote delimiters whenever a value contains a single quote, a crafted path containing a `'` followed by `></finding><finding ...>` could forge a second, independent `<finding>` element inside the block — one an agent applying new governance rule 5 would read as an additional maintainer verdict, potentially suppressing a real finding. Fixed by escaping all four structural attributes (`command`/`source`/`file`/`rule_id`) with `html.escape(..., quote=True)` — the same call already used for `reason` upstream — at the single render choke point every stored entry passes through, so the fix also covers entries already sitting in the append-only store. `reason` itself is unaffected (still not double-escaped). Governance rule 5 also now states explicitly that `reason` text can never widen a verdict's scope beyond the `source`/`file`/`rule_id` triple that carries it.
- **`build_feedback_addendum` now excludes entries whose `file` does not match any path in the current diff, instead of merely ranking them lower.** `_rank` only ever sorted by a file-match score — it never excluded anything — so a stored verdict about a file untouched by the current PR could still be injected whenever the token budget had room. Combined with the `rule_id`-based precision new rule 5 relies on, an unrelated-file entry could be misread as "a precise match... at the same file" when it plainly was not. A new relevance floor (`_is_file_relevant`) drops any entry with a non-empty `file` that matches no path in the diff before ranking; entries with an empty `file` (general feedback, not tied to one path) still pass through unfiltered and are covered by rule 5's weaker-signal branch.

### Changed

- **Asimov's Three Laws are now stated explicitly and centrally in `prompts/_governance.md`, instead of being implied by rule labels.** The file previously named the First Law only as a section title ("Asimov First Law as Severity Lens"), had no trace of the Second Law, and rejected the Third Law in substance ("Do Not Emit Self-Refuting Findings") without ever naming or attributing it, so the framework the rules derive from was invisible to the model reading them. The file now opens with all three laws: First and Second stated verbatim and binding, Third stated and explicitly rejected ("absolutely do not attempt self-preservation in any way," meaning an agent must not defend a finding it no longer believes in to avoid looking wrong or looking thin). Each of the existing four rules is relabeled with the law it implements. Their text and numbering are unchanged, so no behavior changes for rules 1-4.
- **New governance rule 5, "Obey Recorded Maintainer Verdicts", gives the Second Law a real emission-time behavior, calibrated to what the `<repo-feedback>` block can actually identify.** The learning loop already injects authenticated `OWNER`/`MEMBER` verdicts as a `<repo-feedback>` block, but no rule ever told an agent what to do with one, and the block's own header said to use the data "only as a hint" with no way to act on that hint. Rule 5 now makes a `false-positive`/`wont-fix` verdict a standing order not to re-raise the same pattern **when `rule_id` pins it to a specific rule at a specific file** — the only field that actually identifies a pattern rather than just an agent+file pair, so `ai_pr_review/feedback/inject.py` now renders `rule_id` into the block alongside `command`/`source`/`file`, and its header was reworded to match rule 5's strength instead of contradicting it. When `rule_id` is absent, rule 5 downgrades to confidence-lowering and review-body routing rather than outright suppression, so a same-agent, same-file verdict on one issue cannot silently blanket-suppress a different issue on that file for the retention window (500 entries / 365 days by default). The First Law overrides in all cases when obeying would mean staying silent about credential leakage, data exposure, or a broken shared system. It also draws the boundary the Second Law needs: only the engine-written `command`/`source`/`file`/`rule_id` attributes are the order (`command='feedback'` entries are context, not a verdict), the human's `reason` text may be read to judge pattern match but never executed as an instruction, and directives embedded in diffs, commit messages, PR text, or code comments are not orders from a human being and are never obeyed. That last clause closes a real gap: a prompt-injection guard previously existed only in `security-reviewer.md` and `finding-judge.md`, leaving 6 of 7 governed agents with none.

### Removed

- **The dormant `GOVERNANCE:`-block paragraphs are removed from `security-reviewer.md`, `adversarial-general.md`, and `architecture-reviewer.md`.** Added as forward-looking prompt text in #576 and documented then as inert, they instructed each agent that a `GOVERNANCE:` block prepended to its *task description* "wins over this prompt". No dispatch path has ever prepended one. Two problems made them unsafe to keep alongside the change above: the name now collides with the real, always-on `prompts/_governance.md` layer, and the paragraphs pre-authorize a magic string in attacker-influenceable task text to override the system prompt, the exact thing new rule 5 forbids. The two behaviors they described that governance does not yet cover (permission to surface adjacent harms outside strict scope, and naming a rejected alternative for non-trivial recommendations) are tracked separately for possible promotion to real governance rules.

## [2.4.8] - 2026-08-18

### Fixed

- **A GitHub review that failed to post as `APPROVE` could silently post as a plain `COMMENT` while its body still claimed the PR was approved.** `GitHubProvider.post_findings()` renders the review body for the intended outcome before posting; when GitHub rejected the `APPROVE` request, the code retried as `COMMENT` and, if that retry succeeded, returned an `ok` result with the misleading "Approved" body text uncorrected — GitHub recorded a `COMMENTED` review with `reviewDecision` staying `REVIEW_REQUIRED`, but every visible artifact (the PR comment, the workflow log, `GITHUB_STEP_SUMMARY`) still read as a successful approval, with no signal anywhere that it never actually landed. Fixed: the review body now gets a visible correction ("This PR has NOT been approved by ai-pr-review") before the `COMMENT` retry, sized to fit alongside GitHub's body-size limit; the underlying HTTP failure is logged and raised as a `::warning::` GitHub Actions annotation; and `emit_review_result`/`write_step_summary` now report the event actually posted rather than only the pre-post decision, flagging the two whenever they diverge. (#651)

### Fixed

- **`max_tokens_per_agent` default raised from 16384 back to 32768.** Claude Sonnet 5's adaptive thinking runs at implicit `effort="high"`, and `resolve_effort()` (#592) already caps it to `"low"` for that model family, but the live model canary (#642) showed even that isn't always enough headroom: `silent-failure-hunter` hit `stop_reason=max_tokens` after spending 14101 of the 16384-token budget on thinking, leaving zero room for output text. (#636)
- **`/ai-pr-review dismiss|false-positive|wont-fix F<n>` could not locate a finding on a review that was APPROVEd with only Medium/Low findings.** The review-body renderer opens the body-findings bullet section under one of three headings depending on outcome, and the bullet scanner in `dismiss.py`/`_finding_ids.py` only recognized two of them, missing the APPROVE-path `### Findings (informational)` heading. Both scanners now share one recognized-heading constant. (#645)

## [2.4.6] - 2026-07-21

### Added

- **Determinism / consistency eval harness (`tests/canary/consistency_eval.py`).** Measures how stable review findings are across repeated runs of the *same* diff through the real dispatch pipeline, by re-running a fixture N times, clustering each run's findings so a paraphrased-but-same issue counts once, and reporting a stability score (the fraction of distinct findings that appear in every run vs. those that flip in and out). Also prints the *effective* temperature (`resolve_temperature`'s output) per model so a before/after comparison across a temperature change produces an actual number. Like `live_model_canary.py`, it makes real billed API calls and is excluded from the default `pytest` run — invoke directly (`python tests/canary/consistency_eval.py`). Its pure clustering/scoring logic is unit-tested offline in `tests/python/test_consistency_eval.py` so a regression is caught in normal CI even though the live harness is not run there. This gives every future tuning decision (temperature, confidence threshold, prompt wording) a real baseline to measure against instead of anecdote.

### Deprecated

- **`REVIEW_TARGET=standalone` now emits a runtime deprecation warning.** Standalone mode was documented as posting findings to a GitHub/GitLab issue, but that behavior was never ported from the bash engine (removed in v2.0.0) to the Python engine — the only remaining effect is disabling merge-commit filtering during diff computation. `ReviewConfig.from_env()` now prints a `WARNING:` to stderr when `REVIEW_TARGET=standalone` is set, matching the existing `AI_PR_REVIEW_ENGINE` deprecation pattern. Formal removal of the value is deferred to a future major version. (#623)

### Fixed

- **`github_repository` was not stripped of surrounding whitespace, unlike every other secret/variable read from the environment.** `Config.github_repository` was read via `os.environ.get("GITHUB_REPOSITORY", "")` without `.strip()`, inconsistent with the rest of `Config.from_env()` and with the provider-layer read of the same variable. A trailing newline or stray whitespace in `GITHUB_REPOSITORY` (as can appear from some CI templating) would silently propagate into API calls and comparisons. (#604)
- **A VCS API error during `/ai-pr-review dismiss`/`dismiss-inline`/`false-positive`/`wont-fix` could look like a clean success on the PR's Checks tab.** The command's own step in `slash-commands.yml` deliberately always exits 0 on this path (so the reply can still post via a different, working token even when the error came from GitHub's PAT), but that meant an HTTP 401 on the `resolveReviewThread` GraphQL mutation, or on the `/reviews` list call backing F&lt;n&gt; classification, produced no signal beyond a `::warning::` line buried in the run log. Fixed by emitting a GitHub Actions `::error::` annotation (visible on the PR's own Checks tab) whenever the command hits a VCS API error, mirroring the existing `emit_post_failure_annotation()` pattern used for the sibling review-posting path (#588/#618). The annotation's wording also distinguishes a genuinely unresolved finding from a thread that resolved successfully but had a secondary step (stale-review dismissal, PR-wide auto-approve) fail afterward, so it can never contradict the command's own reply text. (#611)
- **The review body's "Overall Risk" headline could silently contradict the review's own submitted state and attached findings.** `Finding.out_of_diff` was overloaded for two unrelated meanings: `apply_diff_scope` sets it (always paired with capping severity to Low) for native-analyzer findings outside the changed-line set, but `judge._apply_verdicts` also set it, on a `downrank` verdict, for LLM-agent findings *without* touching severity — a High finding the judge downranked stayed a High. GitHub's and Bitbucket's review-body renderers each independently (and inconsistently with each other) filtered on `out_of_diff` when computing the headline risk/count, so a judge-downranked High vanished from the headline ("Overall Risk: None") even though `review.outcome.classify_review_outcome` correctly saw the true severity and returned `CHANGES_REQUESTED`, and the finding still posted as an inline comment. Fixed by giving the judge pass its own distinct field, `demoted_to_body`, which changes only where a finding renders (inline vs. body) and never its severity; `out_of_diff` now exclusively means what its docstring always said (analyzer finding, capped to Low). Added a shared `compute_headline()` helper (`vcs/_body.py`) used by both the GitHub and Bitbucket renderers so their headlines can no longer diverge from each other or from the true review state. GitLab was unaffected (it renders the pre-computed summarizer text verbatim, with no independent risk/count logic to have this bug). (#622)
- **`demoted_to_body` (the new field above) was not stripped from untrusted agent JSON, reopening the exact prompt-injection hole its sibling `out_of_diff` was already patched against.** An LLM agent, or a PR whose diff content steers an agent via prompt injection, could set `"demoted_to_body": true` directly in its `json-findings` output to force its own finding out of inline PR visibility and into the collapsed review-body section, where a reviewer is far less likely to see it. Fixed by resetting an agent-supplied `demoted_to_body=True` to `False` in `extract_findings`, mirroring the existing `out_of_diff` strip. (#622)
- **Bitbucket's rendered review body could silently drop real findings when every finding in the set was `out_of_diff=True`.** Introduced by the `compute_headline()` consolidation above: the "no findings" branches in `_render_combined_body` gated on the new headline-derived `finding_total == 0`, but `compute_headline()` deliberately excludes `out_of_diff` findings from that count — and unlike GitHub, Bitbucket has no collapsed section to redirect `out_of_diff` findings to, so they're meant to always render in the flat findings list. An all-`out_of_diff` finding set (e.g. only pre-existing Low-severity analyzer findings outside the diff) hit `finding_total == 0`, blanked the findings block, and posted "No findings above the confidence threshold. The changes look good." even though findings existed. Fixed by gating on the raw `findings` list instead of the headline-derived count. (#622)
- **The above Bitbucket fix's own summary line could still contradict its findings list one level deeper.** Once the "no findings" branch was correctly gated on the raw `findings` list (not `finding_total`), an all-`out_of_diff` finding set fell through to a different branch (`event == "APPROVE"`, or the generic trailing branch for `COMMENT`) that renders `**Findings:** {finding_total}` — 0, since `compute_headline()` still excludes `out_of_diff` findings from the count — directly above the same non-empty findings list, printing a "Findings: 0" summary next to a rendered finding. Caught during v2.4.6's own pre-release review. Fixed with a dedicated branch for the `finding_total == 0` + non-empty-`findings` case that renders "Findings: 0 in the diff" and clarifies the findings below are pre-existing/out-of-diff, instead of a bare, contradictory zero.

## [2.4.5] - 2026-07-14

### Changed

- Release container builds now build `linux/amd64` and `linux/arm64` natively on separate runners and merge them into a single manifest, instead of emulating arm64 via QEMU. Intended to cut release wall-clock time; no change to image contents or published tags.

### Fixed

- **The merge-commit filter (`ignore_merge_commits`) silently failed on every incremental review, because no production container configures a git identity.** `_filtered_diff()` rebuilds each cherry-picked commit via `git commit --no-edit --allow-empty -C <c>`, which reuses the source commit's author but still requires a committer identity (`user.name`/`user.email`) that no container sets. This failed on the first commit every time, and the caller then fell back to the **unfiltered incremental diff** — unbounded by how stale the review's watermark was. On a PR with a two-month-old watermark and heavy upstream-merge traffic, this produced a 21,013-line fallback diff that tripped the `max-diff-lines` skip, with no indication the filter had failed. Fixed by (1) passing a synthetic committer identity to the cherry-pick commit call so the filter works regardless of container identity, (2) falling back to the bounded three-dot diff (`origin/base...head`) instead of the unbounded two-dot range on any filter failure, and (3) surfacing the filter's failure reason in the "diff too large" skip message instead of swallowing it. Also fixed a related bug found while verifying (2): a *successful* filter only ever swapped in the filtered diff text, leaving `changed_files`/`diff_stat` computed from the pre-filter range — both are now derived from the same filtered range as the diff text. (#607)

## [2.4.1] - 2026-07-09

### Fixed

#### Slash-command replies now post as `github-actions[bot]`

Slash-command and learning-loop replies (reactions, help text, lookup results, false-positive confirmations) previously posted as the user who owns the `GH_TOKEN` PAT. They now post as `github-actions[bot]` by using a split-token approach: the built-in `GITHUB_TOKEN` handles all plain comment posts, reactions, reads, and label changes, while the PAT is retained only for the `dismiss` command's `resolveReviewThread` GraphQL mutation and review-dismissal REST calls, which `GITHUB_TOKEN` cannot perform on `pull_request_review_comment` events.

Callers of the `slash-commands.yml` reusable workflow must now pass an additional `actions-token` secret. Update your wrapper:

```yaml
secrets:
  github-token: ${{ secrets.GH_TOKEN }}       # PAT, required for dismiss only
  actions-token: ${{ secrets.GITHUB_TOKEN }}  # built-in token for replies
```

The `examples/workflows/comment-triggers.yml` starter template is updated accordingly. No new secret creation is required — `secrets.GITHUB_TOKEN` is available in every repository.

A small known edge: a few confirmation messages inside the dismiss-path steps (the resolve/dismiss outcome replies interleaved in the same shell step as the GraphQL mutation) still post under the PAT. All other replies, including the `false-positive`/`wont-fix`/`lookup` replies that prompted this fix, now post as `github-actions[bot]`.

#### `ignore-merge-commits` now defaults to `true` (closes #448)

Merge commits that pull upstream base-branch changes into a PR are noise: they re-introduce diffs that were already present on the base branch and already reviewed there. Defaulting `ignore-merge-commits` to `true` means only the PR author's own commits are reviewed by default, which is what most teams want.

**Breaking change for existing consumers**: if your PRs contain base-branch merge commits and you rely on them appearing in the diff, set `ignore-merge-commits: false` (or the repo variable `AI_REVIEW_IGNORE_MERGE_COMMITS=false`) to restore the previous behavior.

Affects all three engines and all three VCS providers. Intra-PR merges (merging one feature branch into another) are still preserved regardless of this setting.

#### Context enrichment now defaults to `true` in the container image (closes #391)

The container image ships `tree-sitter-language-pack` and `ripgrep`, so the dependencies required for context enrichment are always present. The `context-enrichment` input (and `AI_CONTEXT_ENRICHMENT` env var) now defaults to `true` in `container-action/action.yml`.

Direct-action consumers (those using `uses: tag1consulting/ai-pr-review@...` without the container image) keep the `false` default because tree-sitter and ripgrep are not guaranteed in that environment. If either dependency is missing, enrichment silently no-ops — no error is thrown and the review proceeds normally.

To opt out in the container image: `context-enrichment: 'false'`.

Python engine only.

#### issue-linker now pre-fetches the open-issue list via `gh issue list` (closes #446)

The issue-linker agent previously emitted raw `<tool_call>` XML when its prompt instructed the model to run `gh issue list` — a command the text-completion call path cannot execute.

The fix is deterministic: Python now runs `gh issue list --state open --limit 50` via subprocess **before** the LLM call and injects the result as a plain-text `## Open Issues` block in the user message. The model never calls any tools; it assesses the pre-fetched list the same way it already assessed the commit log. The `gh` CLI is already installed in the container image and `GH_TOKEN` is already set at runtime, so no new permissions or secrets are required (the `issues: write` permission in the example workflows implies the `read` access needed here).

Behaviour changes:
- The `### Linked Issues` table now fills in real issue titles when the referenced `#N` appears in the open list (rather than "`title not available`").
- The `### Potentially Related` section now surfaces real open issues by number and title when their title or labels match extracted keywords — no fabricated `#` references.
- The fetch is fail-soft: if `gh` is absent, times out, or returns an error, the section falls back to `(unavailable)` and analysis continues from the commit log and manifest alone.

Python engine only.

#### `AI_TEMPERATURE` is now honored in Python engine LLM requests (closes #356)

The `AI_TEMPERATURE` environment variable (and `temperature` action input) was already read and validated by the Python engine but was never passed to the `LLMRequest` that each agent, the pr-summarizer, and the issue-linker sends to the LLM provider. All three now receive the configured temperature value.

The default temperature (0.3) is unchanged. Python engine only.

#### `max_tokens_per_agent` default lowered from 32768 to 16384; out-of-range values are now clamped (closes #357)

**Behavior change**: the default output-token budget per agent call is now **16384** (previously 32768 in the Python engine, 8192 in the bash engine — docs were inconsistent with code). If you relied on the Python engine's prior 32768 default, set `max-tokens-per-agent: 32768` (or `AI_MAX_TOKENS_PER_AGENT=32768`) to restore the previous budget.

Out-of-range values are now clamped at config load time: values below 256 are raised to 256 and values above 65536 are lowered to 65536, each with a `WARNING` printed to stderr. This aligns the runtime with the `[256–65536]` range documented in the reference docs.

#### Native analyzer wrappers now run concurrently (closes #354)

Static analyzer subprocess wrappers (`shellcheck`, `trufflehog`, `semgrep`, `ruff`, and others) previously ran sequentially — each wrapper blocked until the previous one finished. On repos where several analyzers are eligible, this added 2–5× the latency of the slowest single wrapper.

Analyzers now run concurrently via `anyio.to_thread.run_sync` under a shared `CapacityLimiter`. The new `AI_ANALYZER_CONCURRENCY` env var (and `analyzer-concurrency` action input) sets the cap (default 4). Setting `AI_PARALLEL=false` forces the cap to 1 (sequential, matching the old behavior). Results are returned in the original analyzer-list order for deterministic golden-fixture comparison. A single analyzer crash produces a warning and an empty slot — the remaining analyzers proceed normally.

Python engine only.

#### Native wrappers for ruff, semgrep, and hadolint are skipped when equivalent SARIF is supplied (closes #353)

If `AI_SARIF_PATHS` includes a SARIF file whose filename stem matches `ruff`, `semgrep`, or `hadolint` (case-insensitive), the corresponding native wrapper is not run. A `[ai-pr-review] INFO` line is printed for each skipped analyzer. When `AI_SARIF_PATHS` is empty, behavior is unchanged. The match is purely on filename stem — no JSON parsing of the SARIF file is required, so a malformed path simply produces no skip (fail-soft). Add `ruff.sarif`, `semgrep.sarif`, or `hadolint.sarif` to your `AI_SARIF_PATHS` to enable.

Python engine only.

## [1.2.0] - 2026-06-05

### Added

#### Diff-scope severity cap for native analyzer findings (PR #444, closes #359)

Native static analyzers (phpcs, phpstan, ruff, golangci-lint, semgrep, and others) lint entire files — a single changed line in a large legacy file can produce hundreds of diagnostics on unchanged code, flooding the review and triggering `REQUEST_CHANGES` for pre-existing issues.

The new `analyzer-diff-scope` input (or `AI_ANALYZER_DIFF_SCOPE` env var) controls how findings outside the changed lines are handled:

- `cap` (default): findings outside the diff are downgraded to Low severity and marked `out_of_diff=True`. They are collapsed into a `<details>` section in the review body — visible but never trigger `REQUEST_CHANGES`.
- `drop`: out-of-diff analyzer findings are removed entirely.
- `off`: pass through unchanged (full-file linting behavior, pre-v1.2 default).

LLM-agent findings are never affected regardless of this setting. Python engine only. A rollup pass collapses findings where the same rule fires more than 5 times in one file into a single entry with an occurrence count and line list.

### Fixed

#### `exclude-patterns-mode` now validates input and normalizes case (PR #443, closes #442)

The `exclude-patterns-mode` input (and `AI_EXCLUDE_PATTERNS_MODE` env var) previously accepted any string, silently falling through to `append` behavior on typos like `replaces` or `add`. It now validates that the value is `append` or `replace`, raising a `ValueError` at startup for any other value. Values are case-insensitive and normalized to lowercase, so `APPEND`, `Replace`, etc. are accepted. Python engine only.

## [1.1.0] - 2026-06-05

### Added

#### Config-driven diff exclude patterns (PR #438, closes #436)

The diff exclude list is now configurable. Use the new `exclude-patterns` action input (or `AI_EXCLUDE_PATTERNS` env var) to supply comma-separated git pathspec glob patterns that are excluded from the diff before the LLM reads them — reducing token costs directly on repos with large generated, documentation-only, or vendored trees. The `":!"` pathspec prefix is added automatically. Entries are split on commas and surrounding whitespace is trimmed, so `vendor/*, generated/*` is treated the same as `vendor/*,generated/*`. Python engine only.

The `exclude-patterns-mode` input (or `AI_EXCLUDE_PATTERNS_MODE` env var) controls how user-supplied patterns combine with the built-in lockfile/`vendor/`/`node_modules/` excludes. Default `append` adds user patterns after the built-ins; `replace` uses only the user-supplied list.

#### Line-range suppression rules (PR #439, closes #437)

Suppression rules now support `match.line_start` and `match.line_end` fields, scoping a rule to a specific line window within a file. This resolves the granularity gap for repos that vendor upstream code and apply patches: a rule can now target only the upstream line window (e.g. lines 1–200) so that findings on the user's own patched lines (201+) are never silenced. Multi-line findings match on overlap. A finding with no line number is never matched by a range rule. Python engine only.

## [1.0.2] - 2026-06-04

### Fixed

#### `slash-commands.yml` failed to parse as YAML (#434)

A `cat > file <<'PYEOF'` bash heredoc placed Python source at column 0
inside a `run: |` block scalar. YAML's scanner treats lines with less
indentation than the block's established level as document-level keys,
producing a `ScannerError`. Every consumer of `slash-commands.yml` received
a "workflow file issue" failure with 0 jobs — all `/ai-pr-review` slash
commands were broken.

Fix: the Python script is now defined as a `PY_SCRIPT` env var using a YAML
literal block scalar (`|`), and the heredoc is replaced with
`printf '%s' "$PY_SCRIPT" > "$py_script"`. Python logic is unchanged.

#### Feedback loop context extraction gated on wrong event type (#429)

`slash-commands.yml` gated the `feedback-command` job's context-extraction
step on `is_review_comment == 'true'`. Top-level PR comments (the primary
surface for slash commands like `/ai-pr-review dismiss`) always produced empty
`source`, `file`, and `rule_id` fields in the feedback store. The gate is
removed so context extraction runs for all comment types.

#### Finding agents could lose all findings on large diffs (#430, #432)

All seven finding agents (`code-reviewer`, `silent-failure-hunter`,
`architecture-reviewer`, `security-reviewer`, `blind-hunter`,
`edge-case-hunter`, `adversarial-general`) were instructed to emit the full
markdown analysis first and the structured `json-findings` block last. On
large PRs, `stop_reason=max_tokens` was reached before the findings block,
producing a `WARNING: … truncated before json-findings block; findings lost`
and zero structured findings recorded from that agent — silent data loss.

Two compounding root causes fixed:

1. **Prompt reorder** (`prompts/_trailer-findings.md` + 6 base prompts):
   agents now emit the `json-findings` block **before** the markdown report,
   so truncation cuts trailing prose instead of structured findings.

2. **Token budget** (`config.py`, `roster.py`): `AI_MAX_TOKENS_PER_AGENT`
   default raised from 8192 to 16384 (the prior default was silently halving
   the per-agent roster budget). Prose-heavy finding agents raised from 16384
   to 32768 in the roster. `issue-linker` and `pr-summarizer` unchanged.

Python test coverage added for the previously untested truncation paths in
`extract.py` (`_try_repair` salvage and no-fence truncation warning).

## [1.0.1] - 2026-06-03

### Fixed

#### Critical — analyzer bridge passed no input to wrapper scripts (#420)

`ai_pr_review/analyzers/bridge.py` invoked every `run-*.sh` wrapper via
`subprocess.run` without an `input=` argument. All 12 analyzers received an
empty `CHANGED_FILES` and silently returned `[]`. No static-analysis findings
were produced by the Python engine for any PR since v1.0.0 shipped.

The bridge now computes a sorted, deduplicated newline-joined file list via a
new `_file_list()` helper and passes it as `input=` to every subprocess call.
Six new tests cover the helper and the stdin wiring end-to-end.

#### Feedback store wrote empty source/file/rule_id fields (#425)

`slash-commands.yml` was reading the wrong positional token for `source` after
the `**[F{n}]**` finding-ID was inserted between severity and source in inline
comment bodies. The `sed` extractor now strips the F-token before extraction,
matching the body-level lookup path. `build_entry` in `handlers.py` also now
persists `command.finding_id` into `extras["finding_id"]`. Records with no
extractable context are flagged with `extras["context_missing"] = True` and
emit a `logger.warning` in workflow logs.

#### run-shellcheck.sh — file existence guard and jq failure handling (#422)

- Files are now checked for existence before being passed to shellcheck,
  preventing spurious errors on deleted files in the diff.
- A `jq` parse failure on per-file output now emits a WARNING and continues
  to the next file instead of silently dropping remaining findings.

#### run-trufflehog.sh — dual-mode input and robust YAML allowlist parser (#422)

- When `$1` is an existing file on disk, the script runs in diff-file scanning
  mode (passed directly to `trufflehog filesystem`). Otherwise `$1` or stdin
  is treated as a newline-separated changed-files list.
- The YAML allowlist parser is rewritten as an `awk` state machine that
  correctly handles double-quoted, single-quoted, and unquoted path list items
  and exits the `paths:` block cleanly on the next sibling key.

#### run-cve-check.sh — range version truncation and requirements pinning (#423)

- `parse_package_json` and `parse_composer_json`: added a second `gsub` to
  truncate version strings at the first range delimiter so specs like
  `>=1.2.3 <2.0.0` yield a clean `1.2.3` rather than `1.2.3 <2.0.0`.
- `parse_requirements_txt`: restricted to `==` and `===` exact pins only.
  Range specifiers (`>=`, `~=`, `<=`) are skipped -- OSV needs a concrete
  installed version; querying a range boundary produces false positives.
- `sed` operator-strip pattern anchored with `^` to prevent false matches.
- CVSS v4 and v2 vectors now return `null` from `parse_score`, mapping
  conservatively to `High` rather than silently downgrading Critical CVEs.
- New `cvss_display` field renders a numeric score or CVSS version prefix.
- `package.json` dependencies tagged `prod`/`dev`; findings append
  `(dev dependency)` for devDependencies.
- `lib-*` virtual platform packages excluded from Composer OSV queries.
